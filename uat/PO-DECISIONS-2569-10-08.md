# มติชั่วคราวระหว่างแก้ preship audit — 08/10/2569 (orchestrator ตัดสินแทน · **รอ PO ยืนยัน**)

> ผู้ใช้สั่งให้วนรอบ "แก้ → audit" ข้ามคืนโดยไม่รอ · ทุกข้อเลือกทางที่ปลอดภัย/เปิดเผยข้อมูลน้อยที่สุดที่ยังตรง spec · PO เปลี่ยนได้เมื่อรีวิว

| # | เรื่อง (issue) | ตัดสินชั่วคราว | เหตุผล |
|---|---|---|---|
| P1 | R3-009 ลง audit "login ถูกพัก" | ลง audit `LOGIN_RATE_LIMITED` **ครั้งแรกต่อ (บัญชี/identifier, IP) ต่อ 5 นาที** — คำขอที่ถูกพักซ้ำในช่วงเดียวกันไม่ลงแถวใหม่ · login ผิดรหัส (`INVALID_CREDENTIALS`) / สำเร็จ / logout ยังลงทุกครั้งตาม `05` §13 | audit ลบไม่ได้และเก็บ 5 ปี — ผู้โจมตีไม่ต้อง login ยิงซ้ำเติมแถวได้ไม่จำกัด (ทดสอบ 35 วิได้ 868 แถว) · ยังเห็นสัญญาณการถูกพักครบทุกคู่บัญชี+IP · แนะนำเพิ่ม rate limit ที่ edge (Vercel Firewall) สำหรับ `/api/auth/login` |
| P2 | R3-001/008 ล็อกตรวจรหัส | คิวตรวจรหัสต่อ **บัญชี+IP** ในหน่วยความจำของ instance (แทนล็อก DB) | ล็อก DB ถือ connection ระหว่างเรียก Supabase ⇒ pool ตัน · ข้อจำกัด: หลาย instance พร้อมกันอาจเกินเพดาน 5 ครั้ง/บัญชี+IP ได้ไม่เกินจำนวน instance (เพดานรวมยังนับจาก audit ทุกครั้ง) |
| P3 | R3-003 แก้เคสพร้อมกัน | เพิ่ม error code `CASE_EDIT_CONFLICT` (409) ใน `38` §12 v3.12 — ฟอร์มที่เปิดก่อนคนอื่นบันทึก ถูกปฏิเสธทั้งคำขอ ให้เปิดเคสใหม่แล้วแก้อีกครั้ง (ไม่ merge อัตโนมัติ) | ทางที่ไม่ทำข้อมูลหายแน่นอน · ผู้เรียก API ที่ไม่ส่ง `expectedUpdatedAt` ทำงานแบบเดิม |
