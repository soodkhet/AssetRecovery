## 0. ก่อนเริ่ม (อ่านให้จบก่อนลงมือ)

### 0.1 เส้นทางอัปโหลดไฟล์ (พบจากโค้ด `lib/cases/upload-client.ts`, `components/cases/case-form-modal.tsx`)

```
ฟอร์ม "รับเคส (กรอกมือ)"  ──(1) POST /api/cases ───────────────► สร้างเคส draft (ไฟล์ยัง staged อยู่ในฟอร์ม)
   ไฟล์ที่เลือกไว้ (staged)   ──(2) browser คำนวณ SHA-256 เอง (crypto.subtle) 
                             ──(3) supabase.storage.from('case-documents').upload(...)  ← **browser → Supabase Storage (cloud) ตรง** ด้วย anon key + JWT ผู้ใช้
                                    path = cases/<caseId>/<slot>/<uuid>-<ชื่อไฟล์ ASCII>
                             ──(4) POST /api/cases/:id/documents  { documentType, fileUrl=path, fileHash, originalName, mimeType, sizeBytes }
                                    → แถว case_documents + audit (target_type='case_documents')
```
- **hash คำนวณฝั่ง browser** · API ตรวจแค่รูปแบบ hex 64 ตัว — **ไม่ตรวจว่าไฟล์มีจริงใน Storage และไม่คำนวณ hash ซ้ำ** (ดู 🐞-R2-A)
- ไฟล์ที่อัปโหลดล้มจะขึ้น toast เตือน "อัปโหลดไฟล์ไม่สำเร็จ N ไฟล์" แต่เคสถูกบันทึกไปแล้ว (เปิด "แก้ไข" แล้วแนบใหม่ได้)
- เปิดดูไฟล์ = signed URL 1 ชม. จาก Supabase (`createSignedUrl`) — bucket เป็น private
- ⚠️ **R2 เป็นรอบแรกที่เขียน Supabase Storage จริง** (R1 ไม่มี) · ผู้ใช้อนุญาตแล้ว (STATE 03/10/2569) · ต้องมี bucket `case-documents` + policy ให้ authenticated insert/select (PROGRESS 2.5) — **ถ้า toast ขึ้น "Bucket not found" / "new row violates row-level security" = S2 หยุดรอบ รายงานกลับ**
- restore DB แล้วเล่น R2 ใหม่ ⇒ object เก่าใน bucket เป็นกำพร้า (path มี caseId เก่า) → orchestrator จดเพิ่มท้าย `uat/STATE.md` (ห้ามลบ)
- ตรวจ session: cookie `sb-<ref>-auth-token` ไม่ใช่ httpOnly ⇒ browser client อ่าน JWT ได้ (upload ไปในนามผู้ใช้)

### 0.2 State machine ที่ใช้ (`docs/38` §9–§10 · enum `case_status` `02` §3 — **ไฟล์ `23` ไม่มี state ของเคส** มีแต่ state การเงิน)
```
draft ──review (ธุรการ/approver/manager: ต้องครบข้อมูล+เอกสาร)──► pending_review ──accept (approver)──► approved
                                                                   ├─reject (approver, reason บังคับ)──► rejected
                                                                   └─request_more_info (approver, reason)──► need_info ──return_to_draft──► draft
```
- endpoint เดียว: `PATCH /api/cases/:id/status` body `{ action, reason?, teamId?, teamChangeReason? }`
- ⚠️ `POST /api/cases/:id/accept` **ไม่ใช่การรับเคส** — เป็น "พนักงานกดรับงาน" ของไฟล์ 40 (R3/R4) อย่าสับสน
- ประมาณการรายได้ (`projected_revenue_satang`) **คำนวณตอน `review`** (draft = NULL) และคำนวณซ้ำตอน `accept`
- `suggested_team_id` ตั้งตอน `review` (จังหวัดของ**ที่อยู่ปัจจุบัน**) · `assigned_team_id` + snapshot ค่าบริการ 6 คอลัมน์ ตั้งตอน `accept` เท่านั้น
- audit: review = `status_change` · accept = `approve` (reason = เหตุผลที่กรอก หรือข้อความระบบ `snapshot ค่าบริการอัตโนมัติตอนอนุมัติเคส — เทมเพลต "<ชื่อ>" v<n>`) · reject = `reject` (reason = เหตุผล)
- notification (`90` §6.3): `case.approved` / `case.rejected` → **ผู้สร้างเคส (`uat.admin`)** เท่านั้น · `review` ไม่มี notification

### 0.3 สิทธิ์ที่เกี่ยว (DB จริงหลัง R1 · `lib/cases/permissions.ts`)

- **🐞-R2-B (S4 · code)** ส่งตรวจถูกปัดแล้ว toast แสดงข้อความรวม ไม่ระบุว่าขาดเอกสาร/ช่องไหน ทั้งที่ API ส่ง `missing` / `missingFields` มาให้ (`cases-manager.tsx` `runRowAction()` ใช้แค่ `error.message`) — ยืนยันใน R2.03/R2.06
- **🐞-R2-C (S2/S5 · code)** `changeCaseStatus()` ไม่มี optimistic lock (`update where id` ไม่เช็คสถานะเดิมใน transaction) ⇒ accept/review พร้อมกัน 2 ครั้งอาจผ่านทั้งคู่ → audit + notification ซ้ำ — ยืนยันใน R2.15 (ดับเบิลคลิก) / R2.25 (race)
- **🐞-R2-D (S4 · code vs Rule 05)** หน้า list รับเคสแสดงแค่ "สร้างเมื่อ" — ไม่มีวันเวลา **ส่งตรวจ** (ไม่มีคอลัมน์ submitted_at ใน schema เลย อยู่แค่ audit) และ **รับเคส/ไม่รับเคส** (`reviewed_at` มีใน DTO detail แต่ไม่แสดงทั้ง list และ modal) ⇒ ขัด Rule 05 "action สำคัญ (ส่งงาน/รับงาน) ต้องแสดงวันเวลาบน list"
- **🐞-R2-E (S5 · code)** ตอนรับเคสโดยไม่กรอกเหตุผล audit reason = ข้อความระบบ `snapshot ค่าบริการอัตโนมัติตอนอนุมัติเคส — เทมเพลต "…" vN` และ `caseDecisionMessage()` เอา reason นี้ไปต่อท้าย body แจ้งเตือนถึงธุรการ ⇒ ผู้ใช้เห็นข้อความภายในระบบ (ยืนยันใน R2.20/R2.30)
- ข้อสังเกต (ไม่ใช่บั๊ก): ปุ่ม `+ รับเคส (กรอกมือ)` / `Import ไฟล์` ไม่ได้กรองด้วยสิทธิ์ใน `cases-manager.tsx` — approver/บริหารจะเห็นแล้วกดบันทึกได้ 403 (ยืนยันใน R2.19)

## ❓ จุดที่ spec ไม่ชัด (ห้ามเดา — orchestrator/PO ชี้ขาด)
- **❓-R2-1** DATASET ไม่มีเคสที่ approver **เปลี่ยนทีมจริง** (ทุกเคสใช้ทีมที่ระบบเสนอ) ⇒ เส้นทาง `team_change_reason` ถูกบันทึก + `assigned ≠ suggested` ไม่ถูกพิสูจน์ใน UAT (มีแค่ probe ปัด R2.20/R2.21) · ทางเลือก: ก) ยอมรับ พึ่ง unit test (แนะนำ — ไม่กระทบ R3–R9) ข) เพิ่มเคส C9 (CO1 กรุงเทพ → เปลี่ยนไปทีม B พร้อมเหตุผล) ใช้ต่อใน R3 "มอบหมายทีมว่าง"
- **❓-R2-2** ผู้จัดการทีมเห็นเคสสถานะ `pending_review`/`rejected` ของทีมตัวเองผ่าน `suggested_team_id` (`caseScopeWhere`) — `38` §13 ไม่ระบุว่า manager เห็นเคสก่อนอนุมัติหรือไม่ (`40` เริ่มที่ approved) · ผลต่อ UAT: R2.18/R2.29 คาดหวัง mgr.in เห็น 7 เคส
- **❓-R2-3** การเงิน/บัญชี/บริหาร `GET /api/cases` เห็นทุกเคสพร้อมข้อมูลลูกหนี้ (เลขบัตร/เบอร์/ที่อยู่) ผ่าน `view_master_data` — `38` §13 ให้ "ดูเคสทั้งหมด" แค่ Superadmin/บริหาร · เมนูไม่เปิดให้การเงิน แต่ API เปิด (ลักษณะเดียวกับ BUG-021) · เกี่ยว PDPA `90` §6.2
- **❓-R2-4** ฟอร์มติด `*` ที่ รหัสไปรษณีย์/อำเภอ/ตำบล ของที่อยู่ปัจจุบันและที่อยู่บัตร แต่ readiness (`missingRequiredFields`) ไม่บังคับ — DATASET บอก postal ของที่อยู่บัตรเป็นช่องบังคับ แต่โค้ดไม่บังคับ · UI กับ backend ไม่ตรงกัน ต้องเลือกว่าอะไรถูก
- **❓-R2-5** ประมาณการรายได้ถูกคำนวณตอน `review` ไม่ใช่ตอน "ส่งเคส/สร้าง" (E1 เขียนว่า "ตอนส่งเคส") — ถือว่า "ส่งเคส" = ส่งตรวจ (`review`) ใช่หรือไม่ (step sheet นี้สมมติว่าใช่: draft = NULL)
