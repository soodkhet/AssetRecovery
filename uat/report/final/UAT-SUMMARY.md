## 1. ขอบเขตและวิธีทดสอบ

- **ผู้ทดสอบ**: agent เล่นแทนคนทีละบทบาทตาม step sheet (`uat/steps/R*.md`) ด้วย **Playwright บนเบราว์เซอร์จริง (Chrome)** กดผ่านหน้าจอจริง แล้วตรวจหลังบ้าน (DB, audit log) ทุกขั้น พร้อมภาพหน้าจอใน `uat/shots/`
- **persona 14 บัญชี** + Superadmin: ธุรการ, เจ้าหน้าที่อนุมัติเคส, ผู้จัดการทีม inhouse/outsource, หัวหน้าทีม, พนักงานภาคสนาม 3 คน (inhouse 2, outsource 1), การเงิน, บัญชี, บริหาร, ผู้ใช้บริษัทไฟแนนซ์ 3 คน — ทุกบัญชีถูกบังคับเปลี่ยนรหัสผ่านตอนเข้าครั้งแรก
- **สภาพแวดล้อม**: ฐานข้อมูล dev ในเครื่อง (PostgreSQL) + **Supabase Auth/Storage จริง** (project เดียวกับ staging) · snapshot/restore ทุกปลายรอบ
- **ชุดข้อมูล**: บริษัทไฟแนนซ์ 2 แห่ง (ลิสซิ่ง: Success fee 5% / แคปปิตอล: เหมา 7,490 บาท), ทีม A/B/C, เคส C1–C8 ครอบคลุมทุกกิ่ง (สำเร็จ 4, ไม่สำเร็จ 1, ตีกลับหลักฐาน, ส่งซ้ำ, ไม่รับเคส, timeout), เงินทดรอง ADV1–ADV4
- **ค่าคาดหวัง (golden)**: ยึดพฤติกรรมโค้ดปัจจุบัน (`uat/DATASET.md` v3) — จุดที่ขัดสเปคบันทึกเป็น needs-decision
- ระหว่าง UAT มี fixer แก้บั๊กเป็นชุด (A–R) แล้วเล่นรอบที่ได้รับผลกระทบใหม่ (R4 v3, R5 v2, R6–R10 v3) · verify ล่าสุดก่อน R8: 269 ไฟล์ / 3,431 tests เขียว

## 5. ความเสี่ยงที่เหลือก่อน go-live

1. **Client Portal ยังไม่มี** (`/api/portal/*` ไม่มี) — ผู้ใช้บริษัทไฟแนนซ์ลงจอดที่ `/portal` ว่าง ใช้เมนูภายในแบบอ่านเฉพาะบริษัทตัวเอง · สิทธิ์ 3 ระดับของผู้ใช้บริษัทยังเท่ากัน (O37) → ต้องทำ Phase 7 + R12
2. **มติบัญชีที่ต้องแก้โค้ด (ยังไม่ทำ)**: A1 ค่าใช้จ่ายตามใบเสร็จไม่อยู่ในฐาน WHT (in1 WHT 5,850 → 4,050 satang) · A2 50 ทวิ 1 ใบต่อผู้รับต่อรอบ · A3 ประเภทเงินได้ 40(2)/40(8) ค้างนักบัญชี — ต้องยืนยันก่อนจ่ายเงินจริง
3. **บั๊ก open 22 รายการ** (S2 2, S3 1, S4 7, S5 12) + needs-decision 11 รายการ — ไม่มีตัวที่ทำให้เงินผิด แต่ BUG-139/074/133 ควรแก้ก่อน production
4. **cache รายงานอยู่ใน memory ต่อ process** — บน Vercel หลาย instance การล้าง cache หลัง Adjustment ไปถึงแค่ instance เดียว (ต้องย้ายไป Redis/DB หรือ TTL สั้น)
5. **`CRON_SECRET`** ต้องตั้งบน Vercel staging/production — ถ้าไม่ตั้ง `/api/cron/jobs` เรียกได้โดยไม่มี session นอก production (O40)
6. **ขนาดอัปโหลด Supabase**: ต้องตั้ง Upload file size limit ≥ 100 MB (วิดีโอ) / ≥ 25 MB (เอกสารชุด)
7. **migration 9 ตัว** (`20261003113300`…`20261004140000`) ยังไม่ deploy staging + ต้อง seed สิทธิ์ใหม่ + ตรวจรายได้ซ้ำก่อน deploy (Vercel ไม่ migrate ให้)
8. **ไฟล์ขยะใน Storage** (วิดีโอ/รูป/ใบเซ็นปลอม, Accounting Pack กำพร้า) + ข้อมูล/บัญชี UAT ทั้งชุดต้องลบก่อนใช้งานจริง
9. ด้านควบคุม: ไม่มีแจ้งเตือนถึงผู้อนุมัติเมื่อมีรายการเข้าคิว (BUG-106) · ผู้สร้าง Adjustment อนุมัติรายการตัวเองได้ (ข้อสังเกต R8) · ล็อกงวดก่อนสิ้นเดือนได้ (O25) · login ผิดหลายครั้งไม่ล็อกบัญชี + timing เดา username ได้ (BUG-140)

## 6. ข้อจำกัดของการทดสอบ

- **วันที่จำลอง**: ADV3 เลยกำหนดใช้ dev trigger `asOf 2026-10-05` (audit ระบุ "[จำลองวันที่]") ไม่ได้รอวันจริง · job รายวัน (`daily_field_allowance`) และ timeout มอบหมายสั่งผ่าน dev trigger แทน cron
- **รายงานที่ขึ้นกับวันจริงยังต้องตรวจซ้ำ**: F5 ตั้งแต่ 05/10/2569 (คาด ADV3 1 แถว ฿2,000.00) · O4 ตั้งแต่ 06/10/2569 14:02 (คาด 2 แถว ฿8,490.00)
- **ไม่มี persona สำนักงานบัญชี** — บัญชีตั้งและตอบข้อซักถามเอง · ไม่ได้กด Mark Filed (ยื่นจริงนอกระบบ)
- **ไม่ได้ทดสอบมือถือจริง** — ใช้ Chrome จำลอง iPhone 14 · GPS จำลอง · offline จำลอง · ไฟล์ทดสอบเป็นไฟล์เล็ก/วิดีโอปลอม ไม่มีวิดีโอขนาดใหญ่จริง · ไฟล์ 26 MB ตรวจแค่ฝั่งหน้าจอ
- กิ่ง "ปิดสำเร็จโดยไม่มี expense" (DEC-006/D6) และ SoD สองขั้นทำใน UAT ไม่ได้ — พึ่ง unit test · branch `period_locked` ของ job รายวันทดสอบไม่ได้
- Dashboard (6.6) และ Client Portal (7.x) ยังไม่ได้สร้าง — ข้ามทั้งหมด
- ข้อมูลตัวอย่างไม่มีงวด ก.ย. · ล็อกงวดเดือนปัจจุบัน (ต.ค.) ซึ่ง production อาจไม่อนุญาต
- UAT_PLAN §10.3 แนะนำให้คนทำรอบท้าย: มือถือจริง ~20 นาที + ดูภาพหน้าจอทั้งชุด + ชี้ขาดรายการค้าง
