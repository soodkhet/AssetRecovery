## 1. Summary
ผู้จัดการทีมติดตามทรัพย์มอบหมายเคสที่ "รับแล้ว" จากไฟล์ 38 ให้พนักงานติดตามทรัพย์ในทีมตนเองทีละคนแบบ manual โดยมีข้อมูลประกอบการตัดสินใจ (workload, % ความสำเร็จสะสม, พื้นที่) ประกอบหน้าจอ จากนั้นพนักงานต้อง **กดรับงาน** เพื่อยืนยันรับทราบก่อนเคสจะถูกพิจารณานำเข้าสู่กระบวนการจัดเส้นทาง (ไฟล์ 41)

## 2. Purpose
เป็นจุดเชื่อมระหว่าง "เคสที่ทีมรับแล้ว" (ไฟล์ 38) กับ "งานที่พนักงานต้องลงพื้นที่จริง" (ไฟล์ 41) — ทำให้ผู้จัดการกระจายงานในทีมได้อย่างมีข้อมูลประกอบ และมีจุดยืนยันชัดเจนว่าใครรับผิดชอบเคสไหนก่อนนำไปวางแผนเส้นทาง

## 3. Scope

### 3.1 In Scope
- หน้ารายการเคสที่พร้อมมอบหมาย (มาจากไฟล์ 38 สถานะ `approved`)
- การมอบหมายแบบ manual: ผู้จัดการเลือกพนักงาน 1 คนต่อ 1 เคส จากรายชื่อพนักงานในทีมเดียวกับเคสเท่านั้น (ถ้าผู้จัดการดูแลหลายทีม ระบบกรองตามทีมของเคสที่กำลังมอบหมายอยู่ ไม่ใช่รวมทุกทีมที่ดูแลมาปนกัน)
- ข้อมูลประกอบการตัดสินใจต่อพนักงาน: จำนวนเคส active, % ความสำเร็จสะสม, พื้นที่ที่รับผิดชอบ
- ขั้นตอนพนักงานกดรับงาน (accept_assignment) เป็น state แยกจากการมอบหมาย
- Reassign (เปลี่ยนพนักงานที่รับผิดชอบ) ได้ทุกเมื่อ ไม่จำกัดว่าต้องก่อนหรือหลังพนักงานกดรับงาน พร้อม reason บังคับทุกครั้ง

### 3.2 Out of Scope (ส่งต่อเอกสารอื่น/Sprint ถัดไป)
- การจัดเส้นทาง/จัดรอบงานประจำวัน — เป็นของไฟล์ 41 (Field Tracker Mobile) ทั้งหมด ไฟล์นี้จบที่ "พนักงานกดรับงานแล้ว"
- สถานะ "พร้อมรับงาน/ลาพัก" ของพนักงาน — ยังไม่ทำในรอบนี้
- Auto-suggest พนักงานจาก workload/พื้นที่ (ปัจจุบันเป็น manual ทั้งหมด ผู้จัดการดูข้อมูลประกอบแล้วเลือกเอง)
- Deadline บังคับกดรับงาน — ตั้งใจให้เป็น config ใน Settings แต่ default คือไม่มี deadline (ดู Open Items)
- รายละเอียดขั้น Field Tracking/Evidence (ไฟล์ 41-42) และ Outcome/Close (ไฟล์ 43)

## 4. Actors & Responsibilities
|Actor / Role|Responsibilities|Access Scope|Role Group|
|---|---|---|---|
|Superadmin|ตั้งค่าและแก้ไขได้ทุกส่วน|global|system|
|บริหาร / Executive|ดูภาพรวมการมอบหมายทุกทีม|organization|system|
|ผู้จัดการทีมติดตามทรัพย์ (Manager)|มอบหมาย/เปลี่ยนพนักงานรับผิดชอบเคสในทีมที่ตนเองดูแล|team scope (อาจดูแลได้มากกว่า 1 ทีม — ตาม `Team.manager_ids` ในไฟล์ 09)|**inhouse หรือ outsource** ตาม `Team.side` ของทีมที่ดูแล — คนละ role กับ "เจ้าหน้าที่อนุมัติเคส" (system) ในไฟล์ 38 แม้ชื่อ role จะคล้ายกัน (ดูไฟล์ 06 §7.1 และไฟล์ 07 §7.1)|
|หัวหน้าทีมติดตามทรัพย์ (Supervisor)|ดูข้อมูลการมอบหมาย/workload ของทีมตนเองเสมอ (read scope) — มอบหมาย/เปลี่ยนผู้รับผิดชอบได้หรือไม่ขึ้นกับ Settings (ดู §7.2/§11)|**team scope แคบกว่าผู้จัดการ — สังกัดได้แค่ 1 ทีมเท่านั้น** (ตาม `Team.supervisor_id` ในไฟล์ 09 ซึ่งเป็นค่าเดี่ยว ไม่ใช่ array แบบ `manager_ids`)|**inhouse หรือ outsource** ตาม `Team.side` ของทีมที่สังกัด — คนละ role กับผู้จัดการ (อยู่รองลงมาในลำดับชั้นเดียวกัน)|
|พนักงานติดตามทรัพย์ (Field Agent)|กดรับงานที่ตนเองถูกมอบหมาย|เฉพาะเคสของตนเอง|inhouse หรือ outsource (= role "แอดมิน" ของ Role Group นั้นๆ ตามไฟล์ 07)|
|ระบบ (System)|คำนวณ % ความสำเร็จสะสมและจำนวนเคส active ต่อพนักงาน, กรองรายชื่อพนักงานตามทีม|automated|—|

> **เมนู**: หน้าจอนี้อยู่ใต้เมนู "งานติดตามทรัพย์ > มอบหมายงาน" — เห็นได้ทั้ง 3 Role Group (`system`, `inhouse`, `outsource`) เพราะเจ้าหน้าที่อนุมัติเคส (system) เห็นเมนูนี้ได้ด้วยตามที่ตกลงไว้ใน §3.1 แต่ผู้จัดการทีม inhouse/outsource เห็น**เฉพาะ**เมนูนี้ ไม่เห็นเมนู "รับเคส" ของไฟล์ 38 (ดู Navigation Map ไฟล์ 06 §7.1 สำหรับ matrix เต็ม) — **หัวหน้าทุก Role Group เห็นเมนูนี้ได้เช่นกัน** แต่ scope ข้อมูลแคบกว่าผู้จัดการ (เห็นแค่ทีมเดียวที่สังกัด ไม่ใช่หลายทีม) และความสามารถมอบหมาย/reassign ขึ้นกับ Settings (ดู §6.4, §11, §13)

## 5. Menu & Navigation
- เมนู: `งานติดตามทรัพย์ > มอบหมายและวางแผนงาน`
- รับเคสต่อจากไฟล์ 38 อัตโนมัติผ่าน event `case.approved` — เคสที่ `approved` จากไฟล์ 38 จะปรากฏในหน้านี้ทันทีในสถานะ "พร้อมมอบหมาย"
- เคสที่พนักงานกดรับงานแล้ว จะถูกส่งต่อไปยังไฟล์ 41 เพื่อรอเข้ารอบจัดเส้นทาง

## 6. Data Requirements

### 6.1 Required Fields
|Field|Type|Required|Description / Rule|
|---|---|---|---|
|case_id|uuid|yes|FK ไปเคสจากไฟล์ 38|
|finance_company_id|uuid|yes|คู่ค้า (สืบทอดจากไฟล์ 38)|
|case_ref|string|yes|เลขที่สัญญา (สืบทอดจากไฟล์ 38)|
|assigned_team_id|uuid|yes|ทีมที่ยืนยันจากไฟล์ 38 — ใช้กรองรายชื่อพนักงานที่เสนอในหน้านี้|
|assigned_agent_id|uuid|conditional|พนักงานที่ผู้จัดการเลือก — required ก่อนเปลี่ยนสถานะเป็น `assigned`; เคสมีได้สูงสุด 1 agent ในเวลาเดียวกัน (ไม่แบ่งงานหลายคนต่อเคส)|
|assigned_at|timestamptz|conditional|เวลาที่ผู้จัดการกดมอบหมาย|
|assigned_by|uuid|conditional|ผู้จัดการที่มอบหมาย|
|accepted_at|timestamptz|conditional|เวลาที่พนักงานกดรับงาน — เป็น null จนกว่าพนักงานจะกดรับ (ไม่ถูกล้างค่าเมื่อมี pending_reassignment ที่ยังรอผลอยู่ — เคสยังถือว่า accepted ตามปกติจนกว่าการเปลี่ยนจะสำเร็จจริง)|
|pending_reassignment|object \| null|conditional|คำขอเปลี่ยนผู้รับผิดชอบที่กำลังรอผล — มีค่าเมื่อผู้จัดการกด reassign_case แล้วอยู่ในช่วงรอพนักงานคนเดิมตอบรับ/ปฏิเสธ ดูโครงสร้างใน §6.1.1|
|reassignment_history|array|no|ประวัติการเปลี่ยนพนักงานรับผิดชอบที่**สำเร็จแล้ว**ทุกครั้ง (ไม่จำกัดว่าก่อนหรือหลังกดรับ) แต่ละรายการเก็บ `from_agent_id`, `to_agent_id`, `reassigned_by`, `requested_at`, `resolved_at`, `resolution` (enum: `consented` \| `timeout_auto`), `reason`, `was_accepted_before_reassign` (boolean)|

### 6.1.1 Pending Reassignment Object
เก็บคำขอเปลี่ยนผู้รับผิดชอบที่ส่งไปแล้วแต่ยังไม่ได้ข้อสรุป:
|Field|Type|Description|
|---|---|---|
|requested_by|uuid|ผู้จัดการที่กด reassign_case|
|requested_at|timestamptz|เวลาที่ส่งคำขอ|
|new_agent_id|uuid|พนักงานคนใหม่ที่ผู้จัดการเลือกไว้|
|reason|string|เหตุผลที่ผู้จัดการระบุ (required)|
|expires_at|timestamptz|`requested_at` + ค่า `reassign_timeout_hours` จาก Settings (default 3 ชั่วโมง) — ใช้ตัดสินว่าเกิน timeout หรือยัง|
|status|enum|`waiting_consent` (ค่าเริ่มต้นตอนสร้าง) — เปลี่ยนเป็น `consented`/`declined`/`timeout_auto` แล้วถูกย้ายไปบันทึกใน `reassignment_history` ทันทีที่ resolve (ไม่ค้างอยู่ใน pending object)|
|decline_reason|string \| null|เหตุผลที่พนักงานคนเดิมระบุถ้ากด "ไม่ยินยอม" — null ถ้ายังไม่ resolve หรือ resolve ด้วยทางอื่น|

### 6.2 Agent Decision-Support Fields (แสดงเฉพาะหน้ามอบหมาย ไม่ผูกกับ case)
ข้อมูลต่อไปนี้คำนวณจากฝั่งพนักงาน (ไม่ใช่ของเคส) เพื่อช่วยผู้จัดการตัดสินใจเลือกคนรับผิดชอบ:
|Field|Type|Description|
|---|---|---|
|active_case_count|integer|จำนวนเคสที่พนักงานคนนี้ถือครองอยู่ตอนนี้ (มอบหมายแล้วแต่ยังไม่ปิดเคสตามไฟล์ 43) — ไม่จำกัดเพดาน เป็นข้อมูลให้ดูเฉยๆ|
|success_rate|decimal (0-100%)|**% ความสำเร็จสะสมตลอดการทำงาน** = (จำนวนเคสที่ outcome สำเร็จจากไฟล์ 43 ÷ จำนวนเคสที่ได้รับมอบหมายทั้งหมดสะสม) × 100 — ต้องเป็นค่ากลางที่คำนวณจาก service เดียวกัน เพื่อให้ Report รายบุคคล/ทีมในอนาคตเรียกใช้ค่าเดียวกันได้ ไม่ต้องคำนวณซ้ำ|
|covered_provinces|array of string|พื้นที่/จังหวัดที่พนักงานรับผิดชอบ (สืบทอดจาก team member assignment ในไฟล์ 09)|

### 6.3 Derived / Computed Fields
- ทุก record ที่คำนวณได้ต้องเก็บ `calculation_source` และ `template_version` (สำหรับ success_rate ให้ใช้ pattern เดียวกัน)
- `created_at`/`created_by` ของ assignment record เอง (แยกจาก case) — ใช้ track ว่าใครเป็นคนสร้างการมอบหมายครั้งนี้ เมื่อไหร่

### 6.4 Settings Config — Supervisor Action Permission
ตั้งค่าระดับองค์กร เก็บแยกต่อ Role Group (ไม่ใช่ค่าเดียวคุมทั้งระบบ):
|Field|Type|Default|Description|
|---|---|---|---|
|`supervisor_can_assign_system`|boolean|`true`|หัวหน้า Role Group system ทำ assign_case/reassign_case ได้หรือไม่|
|`supervisor_can_assign_inhouse`|boolean|`true`|หัวหน้า Role Group inhouse ทำ assign_case/reassign_case ได้หรือไม่|
|`supervisor_can_assign_outsource`|boolean|`true`|หัวหน้า Role Group outsource ทำ assign_case/reassign_case ได้หรือไม่|

- ตั้งค่าได้จากเมนู Settings/ตั้งค่าระบบ (Superadmin เท่านั้น)
- ค่านี้คุมเฉพาะ**การกระทำ** (assign_case, reassign_case, respond_reassignment_consent ในฐานะผู้จัดการที่ทำแทน) — **ไม่คุมการมองเห็นข้อมูล** หัวหน้าเห็นเมนู, ตาราง, Kanban, agent picker, ประวัติได้เสมอไม่ว่าค่านี้จะเป็นอย่างไร

## 7. UI Requirements

### 7.1 Page Layout
- หน้า List แสดงเคสที่พร้อมมอบหมาย (จากไฟล์ 38 สถานะ approved) และเคสที่มอบหมายแล้วแต่ยังรอพนักงานกดรับ และเคสที่รับแล้ว — แยกด้วย filter สถานะ ไม่ใช่หน้าแยกกัน
- ปุ่ม "มอบหมาย" เปิด modal เลือกพนักงาน
- **ปุ่ม "ดูภาพรวมทีม" (Kanban Board)** อยู่ที่ระดับเดียวกับปุ่ม filter/search ของหน้า List — เปิดเป็น **full-screen view แทนที่หน้า List ทั้งหน้า** (ไม่ใช่ modal ลอยทับ) พร้อมปุ่มย้อนกลับไปหน้า List ที่ตำแหน่งเดิม
- **ขอบเขตข้อมูลตาม Role**: ผู้จัดการเห็นเคส/พนักงานของทุกทีมที่ตน `manager_ids` ระบุไว้ (อาจหลายทีม) ส่วน**หัวหน้าเห็นเฉพาะทีมเดียวที่ตนสังกัด** (`Team.supervisor_id`) — UI/filter ทีมของหัวหน้าจึงไม่มีตัวเลือก เพราะมีทีมเดียวให้ดูเสมอ

### 7.2 Table Behavior
- รองรับ loading state, empty state, search (case_ref, ชื่อลูกหนี้), filter (สถานะมอบหมาย, ทีม), pagination
- คอลัมน์สถานะ badge: "พร้อมมอบหมาย" / "มอบหมายแล้ว (รอรับ)" / "รับงานแล้ว"
- **คอลัมน์ "ทีม" ต้องแสดง badge Inhouse/Outsource กำกับต่อท้ายชื่อทีมเสมอ** (อ้างอิง `Team.side` จากไฟล์ 09) เพื่อให้ผู้จัดการที่ดูแลหลายทีมแยกแยะได้ทันทีว่าเคสนี้เป็นของทีมในองค์กรหรือทีม outsource — ใช้สีต่างกันชัดเจน (เช่น inhouse = เขียว, outsource = ส้ม) **แสดงเป็นบรรทัดแยกใต้ชื่อทีม ไม่อยู่บรรทัดเดียวกัน** เพื่อไม่ให้คอลัมน์ยาวเกินไป
- **เคสที่มี `pending_reassignment` ค้างอยู่ ต้องมี badge/indicator เพิ่มให้เห็นชัด** (เช่น "รอความยินยอมเปลี่ยนผู้รับผิดชอบ") แยกจาก badge สถานะหลัก เพราะเคสยังเป็น `accepted` ปกติแต่มีคำขอ reassign ค้างอยู่คู่กัน
- **คอลัมน์ "ผู้รับผิดชอบ" ต้องแสดงวันเวลากำกับไว้เสมอ** ไม่ใช่แค่ชื่อพนักงาน — ใต้ชื่อพนักงานให้แสดง:
  - เคส `assigned`: "มอบหมายเมื่อ {assigned_at}"
  - เคส `accepted`: "มอบหมายเมื่อ {assigned_at} • รับงานเมื่อ {accepted_at}"
  - เคส `ready_to_assign`: ไม่มีวันเวลาให้แสดง (ยังไม่มอบหมาย)
  - ใช้ format `DD/MM/YYYY HH:mm` ตามมาตรฐานกลางในไฟล์ 04 §8 เสมอ ไม่สร้าง format แยกเฉพาะโมดูลนี้
- **ปุ่ม action (มอบหมาย/เปลี่ยนผู้รับผิดชอบ) ของหัวหน้าต้องซ่อนไปเลย (ไม่ใช่ disabled)** เมื่อ Settings ของ Role Group นั้นปิดความสามารถนี้ไว้ (`supervisor_can_assign_*` = false ตาม §6.4) — ตามมาตรฐานกลาง `PERMISSION_DENIED` ในไฟล์ 04 §11 ที่ระบุว่า UI ต้อง hide/disable ตาม permission ในกรณีนี้เลือก hide เพื่อไม่ให้หน้าดูรกด้วยปุ่มสีเทาที่กดไม่ได้ — หัวหน้ายังเห็นปุ่ม "ดูประวัติ" และข้อมูลอื่นได้ตามปกติเสมอ (ไม่ผูกกับ settings นี้)
- Responsive: หน้าจอเล็กกว่า `md` สลับเป็น card list เหมือนไฟล์ 38 — การ์ดต้องแสดงวันเวลากำกับแบบเดียวกัน ไม่ตัดออกตอนย่อหน้าจอ และยังคง badge Inhouse/Outsource ของทีมไว้ด้วย (แสดงคนละบรรทัดเช่นเดียวกับ desktop)

### 7.3 Assignment Modal (Manager) — Consolidated: Case Detail + Agent Picker
- เปิดจากปุ่ม "มอบหมาย" ที่แถวเคส
- **modal นี้ต้องแสดงรายละเอียดเคสแบบเต็ม** (ไม่ใช่แค่สรุปย่อ) ก่อนส่วนเลือกพนักงาน เพื่อให้ผู้จัดการตัดสินใจได้โดยไม่ต้องออกจากหน้านี้ไปเปิด modal อื่น — ดึงข้อมูลและรูปแบบการแสดงผลมาจาก "Case Detail / Review Modal" ของไฟล์ 38 (§7.5) ทั้งหมด ได้แก่:
  - สรุปเคส (ลูกหนี้, case_ref, ไฟแนนซ์, ทรัพย์, จังหวัด, มูลหนี้คงเหลือ)
  - ช่องทางติดต่อลูกหนี้และผู้ติดต่ออื่น (ถ้ามี)
  - **เอกสารแนบ — เปิดดูได้จริง** (สัญญา, บัตรประชาชน/เอกสารยืนยันตัวตน, เอกสารอื่น)
  - **รูปสินค้า — เปิดดูภาพขยายได้จริง** แสดงเป็น thumbnail grid
  - สร้างเมื่อ/โดยใคร (created_at/created_by จากไฟล์ 38)
- ต่อจากส่วนรายละเอียดเคส คือส่วน **เลือกพนักงาน** ในหน้าเดียวกัน (ไม่สลับ modal/หน้าใหม่) — แสดงรายชื่อ**เฉพาะพนักงานในทีมเดียวกับเคส** (`assigned_team_id`) เท่านั้น ไม่ดึงพนักงานข้ามทีม แม้ผู้จัดการคนนั้นจะดูแลหลายทีมก็ตาม กรองตามทีมของ**เคสที่กำลังมอบหมาย** เป็นหลัก
- เพราะ modal นี้ยาวกว่าปกติ (รายละเอียดเคสเต็ม + agent picker) ต้อง:
  - แบ่งเป็น section ที่หัวข้อชัดเจน เลื่อนดูได้ลื่น (scrollable body, header/footer ของ modal คงที่)
  - จัดลำดับจากบนลงล่าง: รายละเอียดเคส → เอกสาร/รูปสินค้า → เลือกพนักงาน → ปุ่มยืนยัน
- หน้า List หลักของโมดูลนี้ (ก่อนเปิด modal) ต้องแสดงเคสจาก**ทุกทีมที่ผู้จัดการดูแล** ได้ในหน้าเดียว (ตาม `Team.manager_ids` — ผู้จัดการ 1 คนอาจอยู่ในหลายทีม) พร้อม filter เลือกทีมได้ถ้าต้องการดูทีมใดทีมหนึ่งเฉพาะ
- แต่ละพนักงานแสดงเป็น card/row พร้อมข้อมูลประกอบ: ชื่อ, **ชื่อทีมที่สังกัด + badge Inhouse/Outsource**, จำนวนเคส active ตอนนี้, % ความสำเร็จสะสม, พื้นที่ที่รับผิดชอบ — ให้ผู้จัดการเปรียบเทียบกันได้ในหน้าเดียว (badge ทีมสำคัญเมื่อผู้จัดการดูแลหลายทีมที่อาจมีทั้ง inhouse และ outsource ปนกัน)
- **แต่ละพนักงานในรายการต้องมีปุ่ม/ไอคอน toggle "ดูเคสที่ถืออยู่"** — กดแล้วขยาย (expand) แสดงรายการเคสที่พนักงานคนนั้นถือครองอยู่จริง ณ ปัจจุบัน โดยแต่ละเคสในรายการต้องมี: ชื่อลูกหนี้, จังหวัด, ชื่อสินค้า/ทรัพย์, มูลหนี้คงเหลือ — เพื่อให้ผู้จัดการเห็นข้อมูลจริงประกอบการตัดสินใจ ไม่ใช่ดูแค่ตัวเลข `active_case_count` ลอยๆ — ขยายได้พร้อมกันหลายคนในรายการเดียวกัน (ไม่ใช่ accordion ที่เปิดได้ทีละคน) — **แต่ละเคสในรายการที่ขยายต้องมีปุ่ม "ดูรายละเอียด" ต่อท้าย** เปิด case detail view แบบอ่านอย่างเดียว (read-only — ไม่มีปุ่ม assign/reassign ซ้อนอยู่ในนั้น) เพื่อให้ผู้จัดการตรวจสอบเคสที่พนักงานถืออยู่ได้ละเอียดขึ้นโดยไม่ต้องออกจาก flow การเลือกผู้รับผิดชอบที่กำลังทำอยู่
- ผู้จัดการคลิกเลือกพนักงาน 1 คน แล้วกดยืนยัน → สถานะเคสเปลี่ยนเป็น `assigned`
- **ถ้าเคสนี้กำลังจะ reassign และเคสปัจจุบันมีสถานะ `accepted` แล้ว**: ปุ่มยืนยันต้องเปลี่ยนข้อความเป็น "ส่งคำขอเปลี่ยนผู้รับผิดชอบ" (ไม่ใช่ "ยืนยันเปลี่ยน" แบบเดิม) พร้อมข้อความเตือนในหน้าว่าจะไม่เปลี่ยนทันที ต้องรอพนักงานคนเดิมตอบรับหรือรอ timeout ก่อน — ต้องกรอก reason เสมอ
- **ถ้าเคสปัจจุบันยังเป็น `assigned`** (ยังไม่ accepted): ปุ่มยืนยันคงข้อความ "ยืนยันเปลี่ยน" ตามเดิม เพราะเปลี่ยนทันทีไม่ต้องขอความยินยอม

### 7.4 Agent Accept UI
- พนักงานเห็นรายการเคสที่ตนเองถูกมอบหมายแต่ยังไม่กดรับ พร้อมปุ่ม "รับงาน" (accept_assignment) ชัดเจน
- หลังกดรับ เคสจะหายจากรายการ "รอรับ" และไปอยู่ในสถานะที่พร้อมให้ไฟล์ 41 ดึงไปจัดเส้นทางในรอบถัดไป
- **พนักงานต้องเห็นรายการคำขอเปลี่ยนผู้รับผิดชอบที่รออยู่ (ถ้ามี)** แยกจากรายการรับงานปกติ — แสดงเหตุผลที่ผู้จัดการระบุ, เวลาที่เหลือก่อนหมดเขต (`expires_at`), ปุ่ม "ยินยอม" และ "ไม่ยินยอม" (ต้องกรอกเหตุผลเมื่อกดไม่ยินยอม)

### 7.5 Kanban Board — ภาพรวม Workload ของทีม
- เข้าถึงจากปุ่ม "ดูภาพรวมทีม" ในหน้า List (§7.1)
- **แบ่งคอลัมน์ตามพนักงาน** (1 คอลัมน์ = 1 คน) ไม่ใช่ตามสถานะเคส — หัวคอลัมน์แสดงชื่อพนักงาน, **ชื่อทีมที่สังกัด + badge Inhouse/Outsource**, % ความสำเร็จสะสม, จำนวนเคสในมือ
- แต่ละคอลัมน์มีการ์ดเคสเรียงอยู่ — การ์ดแสดง: ชื่อลูกหนี้, จังหวัด, ชื่อสินค้า/ทรัพย์, มูลหนี้คงเหลือ, สถานะ (assigned/accepted/มี pending_reassignment)
- **ไม่ต้องรองรับ drag-and-drop** — เป็น read-only view สำหรับดูภาพรวมเท่านั้น การ reassign ยังทำผ่าน flow ปกติ (modal ที่มีขั้นยืนยัน/ขอความยินยอมตาม §7.3) คลิกที่การ์ดเพื่อเปิดไปยัง modal มอบหมาย/reassign ของเคสนั้นได้
- **Filter ที่ต้องมี**: ทีมที่ดูแล (ถ้าดูแลหลายทีม), ชื่อพนักงาน, จังหวัด, **สถานะงาน** (มอบหมายแล้ว-รอรับ / รับงานแล้ว / รอความยินยอมเปลี่ยนผู้รับผิดชอบ) — filter จังหวัดและสถานะกรองที่ระดับการ์ดเคส (ซ่อนการ์ดที่ไม่ตรงเงื่อนไข แต่ยังโชว์คอลัมน์พนักงานไว้ แม้ไม่มีเคสตรงเงื่อนไขเหลือก็ตาม เพื่อให้เห็นว่าใครมีงานบ้าง)
- Responsive: บนมือถือ/จอเล็ก สลับจาก columns แนวนอนเป็น stack แนวตั้งทีละคอลัมน์ เลื่อนดูได้

## 9. Workflow
```
[ไฟล์ 38: case.approved] → พร้อมมอบหมาย → (ผู้จัดการเลือกพนักงาน) → assigned (รอรับ)
                                            assigned (รอรับ) → (พนักงานกดรับงาน) → accepted → [ส่งต่อไฟล์ 41 รอเข้ารอบจัดเส้นทาง]

   [Reassign เคสที่ยัง "assigned" — ไม่ต้องผ่านความยินยอม]
   assigned (รอรับ) → reassign_case (พร้อม reason) → assigned (รอรับ, คนใหม่) ทันที

   [Reassign เคสที่ "accepted" แล้ว — ต้องผ่านขั้นยินยอม]
   accepted → reassign_case (พร้อม reason) → สร้าง pending_reassignment (status: waiting_consent)
            → เคสยังเป็น accepted ของคนเดิม ทำงานต่อได้ตามปกติ ระหว่างรอผล
            ├─ คนเดิมกด "ยินยอม" → assigned (รอรับ, คนใหม่) — ล้าง accepted_at, ลบ pending_reassignment
            ├─ คนเดิมกด "ไม่ยินยอม" + decline_reason → accepted (คนเดิมเหมือนเดิม) — ลบ pending_reassignment, ไม่มีอะไรเปลี่ยน
            └─ ไม่ตอบจนครบ expires_at (default 3 ชม., ตั้งค่าได้) → ระบบ auto-resolve → assigned (รอรับ, คนใหม่) — ล้าง accepted_at, ลบ pending_reassignment
```
- ไม่มี auto-assign และไม่มี auto-suggest ตอนมอบหมายครั้งแรก — ทุกการมอบหมายเป็นการเลือกของผู้จัดการ 100% (auto-resolve มีเฉพาะกรณี timeout ของ reassignment ที่ขอไปแล้วเท่านั้น ไม่ใช่การมอบหมายเริ่มต้น)
- **Reassign เคสที่ยัง `assigned` (ไม่ accepted)**: ทำทันที ไม่ต้องขอความยินยอม เพราะพนักงานยังไม่เริ่มงานจริง — เงื่อนไขเดียวคือต้องระบุ reason
- **Reassign เคสที่ `accepted` แล้ว**: ต้องผ่านขั้นขอความยินยอมจากพนักงานคนเดิมก่อนเสมอ — ไม่เปลี่ยนทันที เพื่อป้องกันการดึงงานจากคนที่กำลังลงพื้นที่ติดตามอยู่โดยไม่รู้ตัว
- ระหว่างที่ `pending_reassignment` ยังรอผล เคสยังถือว่าเป็นของพนักงานคนเดิมเต็มรูปแบบ ทำงาน/อัปเดตผลในไฟล์ 41-42 ได้ตามปกติไม่ถูกจำกัด
- ถ้าเคสเคย `accepted` มาก่อนแล้วถูก reassign สำเร็จ (ไม่ว่าด้วยความยินยอมหรือ timeout) และคนเดิมได้เริ่มงานภาคสนามไปแล้ว (เช่น มีข้อมูลในไฟล์ 41/42) ต้องดูแลความสอดคล้องของข้อมูลภาคสนามเดิมร่วมกับไฟล์ 41 ด้วย — ระบุไว้เป็น Open Item เพราะอยู่นอก scope ของไฟล์นี้
- เคสที่ยังไม่ accepted (รวมถึงเคสที่ accepted แล้วแต่ reassign สำเร็จจนสถานะกลับไป assigned) จะไม่ถูกดึงเข้ารอบจัดเส้นทางของไฟล์ 41 ไม่ว่ารอบนั้นจะปิดรับไปแล้วหรือยัง — ต้องรอ accepted (ใหม่) ก่อนเท่านั้น

## 10. Status / State Machine
|State|Meaning|Allowed Next States|Trigger|
|---|---|---|---|
|ready_to_assign|เคสรับแล้วจากไฟล์ 38 พร้อมมอบหมาย|assigned|assign_case|
|assigned|มอบหมายแล้ว รอพนักงานกดรับ|assigned (คนใหม่) / accepted|reassign_case (ทันที) / accept_assignment|
|accepted|พนักงานกดรับงานแล้ว|accepted (มี pending_reassignment ค้างอยู่) / assigned (คนใหม่ รอรับใหม่)|reassign_case (สร้าง pending_reassignment) / respond_reassignment_consent (ยินยอม) / resolve_reassignment_timeout|
|accepted + pending_reassignment|รอผลคำขอเปลี่ยนผู้รับผิดชอบ — ทำงานต่อได้ตามปกติ|accepted (ไม่ยินยอม — pending ถูกลบ) / assigned (ยินยอม หรือ timeout)|respond_reassignment_consent / resolve_reassignment_timeout|

> หมายเหตุ: state เหล่านี้เป็นสถานะของ **assignment** ซึ่งเป็น sub-state ต่อจาก case.status = `approved` ของไฟล์ 38 ไม่ใช่การแทนที่ state machine ของไฟล์ 38 — `accepted` ไม่ใช่ state ปิดตาย (terminal) เพราะ reassign (ผ่านขั้นยินยอม/timeout) สามารถดึงกลับไป `assigned` ได้เสมอ — `accepted + pending_reassignment` ไม่ใช่ state แยกในระดับ `case.assignment_status` แต่เป็น sub-flag ที่มี `pending_reassignment` ไม่เป็น null

## 11. Business Rules
- **1 เคส : 1 พนักงานเท่านั้น** ห้ามแบ่งงานเคสเดียวกันให้หลายคนพร้อมกัน
- **ไม่จำกัดจำนวนเคส active ต่อพนักงาน (concurrent)** — พนักงานรับเคสค้างได้ไม่จำกัดจำนวน
- **กรองรายชื่อพนักงานตามทีมของเคสเท่านั้น** — หน้ามอบหมายต้องแสดงเฉพาะพนักงานที่เป็นสมาชิกของ `assigned_team_id` ของเคสที่กำลังมอบหมาย ไม่ดึงพนักงานข้ามทีมมาแสดง แม้ผู้จัดการคนนั้นจะดูแลหลายทีมพร้อมกันก็ตาม (ดูแลหลายทีม = เห็นเคสของหลายทีมในหน้า List แต่ตอนมอบหมายแต่ละเคสยังกรองตามทีมของเคสนั้นเสมอ)
- **% ความสำเร็จคำนวณสะสมตลอดการทำงาน** ไม่ใช่ตามช่วงเวลา (เช่น ไม่ใช่เฉพาะเดือนนี้/ปีนี้) — นับรวมทุกเคสที่ปิดแล้วตั้งแต่เริ่มทำงาน
- **ต้องกดรับงานก่อนเข้าสู่กระบวนการจัดเส้นทาง** — นี่คือ hard gate ระหว่างไฟล์ 40 กับไฟล์ 41 เคสที่ `assigned` แต่ยังไม่ `accepted` จะไม่ปรากฏในรอบจัดเส้นทางใดๆของไฟล์ 41
- **Reassign เคสที่ยัง `assigned` (ยังไม่ accepted)**: ทำได้ทันที ไม่ต้องขอความยินยอม — เงื่อนไขเดียวคือต้องระบุ reason
- **Reassign เคสที่ `accepted` แล้ว ต้องผ่านขั้นขอความยินยอมจากพนักงานคนเดิมเสมอ** — ผู้จัดการกด reassign_case แล้วระบบสร้าง `pending_reassignment` แทนการเปลี่ยนทันที เพื่อป้องกันการดึงงานจากพนักงานที่อาจกำลังลงพื้นที่ติดตามอยู่โดยไม่รู้ตัว (เปลี่ยนจากแนวคิดเดิมที่เคยให้ reassign ได้ทันทีทุกสถานะ — ดูเหตุผลที่ปรับใน §21)
- **ระหว่างรอผลคำขอเปลี่ยนผู้รับผิดชอบ พนักงานคนเดิมยังถือเคสและทำงานต่อได้ตามปกติ** ไม่ถูก freeze หรือจำกัดสิทธิ์ใดๆ ในไฟล์ 41-42
- **ผลของ pending_reassignment มี 3 ทาง**: (1) คนเดิมกด "ยินยอม" → เปลี่ยนทันที (2) คนเดิมกด "ไม่ยินยอม" พร้อม `decline_reason` → ยกเลิกคำขอ ไม่มีอะไรเปลี่ยน (3) ไม่ตอบจนครบเวลา `expires_at` → **ระบบ auto-assign ให้คนใหม่ที่ผู้จัดการเลือกไว้โดยอัตโนมัติ** (resolution = `timeout_auto`)
- **ระยะเวลารอความยินยอมก่อน timeout**: ค่า default คือ **3 ชั่วโมง** จากเวลาที่ส่งคำขอ (`requested_at`) — ตั้งค่าปรับได้ใน Settings/ตั้งค่าระบบ (ค่ากลางระดับองค์กร ใช้ร่วมกับ deadline กดรับงานครั้งแรกที่เป็น Open Item อยู่แล้ว แต่เป็นค่าคนละตัวกัน)
- **Reassign สำเร็จ (ไม่ว่าด้วยความยินยอมหรือ timeout) จะรีเซ็ตสถานะกลับเป็น `assigned`** เสมอ และล้างค่า `accepted_at` เป็น null เพราะพนักงานคนใหม่ยังไม่ได้ยืนยันรับทราบ ต้องกดรับงานใหม่อีกครั้ง
- **ไม่มี deadline บังคับกดรับงานครั้งแรกในรอบนี้** — ค่า default คือไม่จำกัดเวลา แต่ต้องออกแบบเป็นช่อง config ใน Settings เผื่ออนาคตเปิดใช้ (ดู Open Items) — แยกจาก timeout ของ reassignment consent ข้างต้น
- **หัวหน้าเห็นเมนูนี้ได้เสมอ แต่ทำ assign_case/reassign_case ได้หรือไม่ขึ้นกับ Settings ต่อ Role Group** (`supervisor_can_assign_system/inhouse/outsource` ตาม §6.4) — ค่า default คือเปิด (ทำได้) ถ้าปิดไว้ หัวหน้าจะเห็นข้อมูลทั้งหมดได้ตามปกติ (รายการเคส, Kanban, agent picker, ประวัติ) แต่ปุ่ม action จะถูกซ่อนไป
- **ขอบเขตข้อมูลของหัวหน้าจำกัดที่ทีมเดียว** (`Team.supervisor_id`) ต่างจากผู้จัดการที่เห็นได้หลายทีม (`Team.manager_ids`) — แม้ Settings เปิดให้หัวหน้า assign/reassign ได้ ก็ทำได้แค่ในทีมที่ตนสังกัดเท่านั้น เหมือนกฎ team-scope ของผู้จัดการ

## 12. Validation & Error Handling
|Scenario|Validation / Error|System Behavior|
|---|---|---|
|มอบหมายเคสให้พนักงานนอกทีมของเคส|`ASSIGNMENT_TEAM_MISMATCH`|reject — ไม่อนุญาตให้เลือกพนักงานที่ไม่ใช่สมาชิกทีมที่ผูกกับเคสนี้ (ใช้ทีมของเคส ไม่ใช่ทีมใดก็ได้ที่ผู้จัดการดูแล)|
|มอบหมายเคสที่ยัง assigned/accepted อยู่ (ไม่ใช่ reassign)|`ASSIGNMENT_ALREADY_EXISTS`|ต้องใช้ action reassign_case แทน assign_case ถ้าเคสมี agent อยู่แล้ว ไม่ว่าสถานะปัจจุบันจะเป็น assigned หรือ accepted|
|Reassign ไม่กรอก reason|`ASSIGNMENT_REASON_REQUIRED`|reject การบันทึก ต้องระบุเหตุผลทุกครั้งที่เปลี่ยนคนรับผิดชอบ ไม่ว่าจะ reassign ตอนสถานะ assigned หรือ accepted|
|Reassign เคสที่ accepted แล้ว ขณะที่มี `pending_reassignment` ค้างอยู่แล้ว|`REASSIGNMENT_ALREADY_PENDING`|reject — ห้ามส่งคำขอเปลี่ยนซ้ำซ้อนระหว่างที่ยังมีคำขอเดิมรอผลอยู่ ต้องรอให้คำขอเดิม resolve ก่อน (ยินยอม/ไม่ยินยอม/timeout)|
|พนักงานคนอื่น (ไม่ใช่ผู้ถือเคสปัจจุบัน) พยายาม respond_reassignment_consent|`PERMISSION_DENIED`|reject — เฉพาะพนักงานที่ถูกขอเปลี่ยนเท่านั้นที่ตอบคำขอได้|
|กด "ไม่ยินยอม" โดยไม่กรอก `decline_reason`|`DECLINE_REASON_REQUIRED`|reject การบันทึก ต้องระบุเหตุผลเมื่อปฏิเสธคำขอ|
|ตอบคำขอ (ยินยอม/ไม่ยินยอม) หลังจาก `expires_at` ผ่านไปแล้ว|`REASSIGNMENT_ALREADY_TIMED_OUT`|reject การตอบ — ระบบได้ auto-resolve เป็น `timeout_auto` ไปแล้ว ไม่รับการตอบที่มาช้า|
|reassign/กดรับงาน/ตอบคำขอ กับเคสที่ยังไม่มีการมอบหมายที่ใช้งานอยู่ (หรือไม่ใช่เคสที่ตนถูกมอบหมาย)|`ASSIGNMENT_NOT_FOUND`|reject (404) — ต้องมอบหมายก่อนจึงจะเปลี่ยนผู้รับผิดชอบ/กดรับได้ · ไม่ leak ว่าเคสนั้นเป็นของใคร|
|กดรับงานซ้ำ หรือสั่ง action ที่สถานะการมอบหมายปัจจุบันไม่รองรับ|`ASSIGNMENT_INVALID_STATUS`|reject — ตรวจสถานะล่าสุดของการมอบหมาย (§10) แล้วลองใหม่|

## 14. Audit Log
ทุก mutation บันทึก `actor_id`, `role`, `action`, `before`, `after`, `reason` (เมื่อมี) รวมถึง:
- การมอบหมายเคสครั้งแรก (assign_case)
- การ reassign เคสที่ยัง `assigned` (เปลี่ยนทันที พร้อม reason)
- **การส่งคำขอเปลี่ยนผู้รับผิดชอบเคสที่ `accepted`** (สร้าง `pending_reassignment` พร้อม reason ของผู้จัดการ)
- **การตอบคำขอของพนักงานคนเดิม** — ยินยอม / ไม่ยินยอม (พร้อม `decline_reason`) / หรือ auto-resolve จาก timeout — บันทึกแยกจากกันชัดเจนว่า resolution เป็นแบบไหน
- การกดรับงานของพนักงาน (accept_assignment พร้อม `accepted_at`)

## 15. Notifications
- แจ้งพนักงานเมื่อถูกมอบหมายเคสใหม่ ("คุณได้รับมอบหมายเคส [case_ref] กรุณากดรับงาน")
- แจ้งผู้จัดการเมื่อพนักงานกดรับงานแล้ว (เพื่อ track ว่าเคสพร้อมเข้าสู่การจัดเส้นทาง)
- **แจ้งพนักงานคนเดิมทันทีที่มีคำขอเปลี่ยนผู้รับผิดชอบเคสที่ตนถือ (accepted)** พร้อมเหตุผลที่ผู้จัดการระบุ และเวลาที่ต้องตอบก่อนหมดเขต (`expires_at`)
- **แจ้งผู้จัดการเมื่อพนักงานตอบคำขอ** (ยินยอม/ไม่ยินยอม พร้อมเหตุผล) หรือเมื่อระบบ auto-resolve จาก timeout
- **แจ้งพนักงานคนใหม่** เมื่อคำขอ resolve สำเร็จ (ยินยอมหรือ timeout) ว่าตนได้รับมอบหมายเคสนี้แล้ว ให้กดรับงาน

## 16. Integration Points
- event `case.approved` (จากไฟล์ 38) → สร้าง assignment record สถานะ `ready_to_assign` ในโมดูลนี้
- event `assignment.accepted` → ส่งต่อไฟล์ 41 (Field Tracker Mobile) เพื่อให้เคสพร้อมถูกดึงเข้ารอบจัดเส้นทางถัดไป
- event `case.outcome_confirmed` (จากไฟล์ 43) → ใช้คำนวณ `success_rate` สะสมของพนักงานที่รับผิดชอบเคสนั้น
- **scheduled job** ตรวจ `pending_reassignment.expires_at` ที่เลยกำหนดแล้วยังไม่ resolve → trigger `resolve_reassignment_timeout` อัตโนมัติ (ความถี่ในการตรวจ เช่น ทุก 5-15 นาที เป็นรายละเอียด implementation)

## 19. Acceptance Criteria
- เคสจากไฟล์ 38 (approved) ปรากฏในหน้ามอบหมายได้ถูกต้อง
- รายชื่อพนักงานที่เสนอกรองตามทีมของเคสถูกต้อง ไม่หลุดข้ามทีม
- ข้อมูลประกอบ (active_case_count, success_rate, covered_provinces) แสดงถูกต้องตรงกับข้อมูลจริง
- มอบหมายได้ 1 เคส : 1 พนักงานเท่านั้น
- Reassign ทำได้ทุกเมื่อพร้อม reason บังคับเสมอ — reassign หลัง accepted รีเซ็ตสถานะกลับเป็น assigned ถูกต้อง
- พนักงานกดรับงานได้ และเคสไม่ถูกดึงเข้ารอบจัดเส้นทางก่อนกดรับ
- **Modal มอบหมาย/reassign แสดงรายละเอียดเคสเต็ม (รวมเอกสารและรูปสินค้าที่เปิดดูได้จริง) ในหน้าเดียวกับส่วนเลือกพนักงาน** ผู้จัดการไม่ต้องออกจาก modal ไปเปิดที่อื่นเพื่อดูข้อมูลเคสก่อนตัดสินใจ
- Audit log ครบทุก mutation สำคัญ

## 21. การตัดสินใจที่เกี่ยวข้อง (Decisions)

- **1 เคส : 1 พนักงานเท่านั้น** ห้ามแบ่งงานเคสเดียวกันให้หลายคนพร้อมกัน — ไม่จำกัดจำนวนเคส active ต่อพนักงาน (concurrent) (§11)
- **ต้องกดรับงาน (accept_assignment) ก่อนเข้าสู่กระบวนการจัดเส้นทางเสมอ** — เป็น hard gate ระหว่างไฟล์ 40 กับไฟล์ 41 (§9, §11)
- **Reassign เคสที่ยัง `assigned` ทำได้ทันทีไม่ต้องขอความยินยอม แต่เคสที่ `accepted` แล้วต้องผ่านขั้นขอความยินยอมจากพนักงานคนเดิมเสมอ** — ป้องกันดึงงานจากพนักงานที่อาจกำลังลงพื้นที่อยู่โดยไม่รู้ตัว (§11, §21 เดิม)
- **ระยะเวลารอความยินยอมก่อน timeout default 3 ชั่วโมง** จาก `requested_at` — ปรับได้ใน Settings ระดับองค์กร แยกจาก deadline กดรับงานครั้งแรก (§11)
- **Reassign สำเร็จ (ยินยอมหรือ timeout) รีเซ็ตสถานะกลับเป็น `assigned` เสมอ** และล้าง `accepted_at` — พนักงานคนใหม่ต้องกดรับงานใหม่อีกครั้ง (§11)
- **ไม่มี deadline บังคับกดรับงานครั้งแรกในรอบนี้** — default ไม่จำกัดเวลา แต่เตรียมช่อง config ใน Settings ไว้รองรับอนาคต (§11, ดู Open Items)
- **หัวหน้าทีมเห็นเมนูนี้ได้เสมอ แต่ทำ assign_case/reassign_case ได้หรือไม่ขึ้นกับ Settings ต่อ Role Group** (`supervisor_can_assign_system/inhouse/outsource` — default เปิด) — การมองเห็นข้อมูลไม่ผูกกับ Settings นี้ (§6.4, §11)
- **ขอบเขตข้อมูลของหัวหน้าจำกัดที่ทีมเดียว** (`Team.supervisor_id`) ต่างจากผู้จัดการที่ดูแลได้หลายทีม (`Team.manager_ids`) (§11)
- **% ความสำเร็จคำนวณสะสมตลอดการทำงาน ไม่ใช่ตามช่วงเวลา** — ใช้ service เดียวกันเพื่อให้ Report ในอนาคตเรียกค่าเดียวกันได้ (§6.2)

## 22. สิ่งที่ยังต้องตัดสินใจ (Open Items)

1. **Deadline กดรับงานครั้งแรก**: รอบนี้ default ไม่มี deadline แต่ต้องเตรียมช่อง config ใน Settings/ตั้งค่าระบบ เพื่อเปิดใช้ในอนาคตได้โดยไม่ต้องแก้โครงสร้างใหม่ — ต้องออกแบบรายละเอียดว่าถ้าเลยเวลาแล้วจะเกิดอะไร เมื่อ requirement ชัดเจนขึ้น (แยกจาก `reassign_timeout_hours` ที่ออกแบบไว้แล้วในรอบนี้)
2. **ความสอดคล้องของข้อมูลภาคสนามเมื่อ reassign สำเร็จหลัง accepted**: เคสที่ reassign สำเร็จ (ด้วยความยินยอมหรือ timeout) ออกจากพนักงานคนเดิมหลังจากที่เขาอาจเริ่มงานภาคสนามไปแล้ว (มีข้อมูลในไฟล์ 41/42) ต้องออกแบบร่วมกับไฟล์ 41 ว่าจะจัดการข้อมูล/ความคืบหน้าที่คนเดิมทำไว้อย่างไร
3. **สถานะพร้อมรับงาน/ลาพักของพนักงาน**: ยังไม่มีระบบนี้ — เมื่อมีจะช่วยกรอง/เตือนผู้จัดการไม่ให้มอบหมายเคสให้คนที่ไม่พร้อมได้แม่นยำขึ้น และอาจเชื่อมกับเหตุผลการ reassign (เช่น auto-fill "ลาป่วย" ถ้าพนักงานตั้งสถานะลาไว้)
4. **Auto-suggest พนักงาน**: ปัจจุบันเป็น manual 100% หากในอนาคตต้องการ auto-suggest จาก workload/พื้นที่ ต้องออกแบบ algorithm แยกเหมือนที่ทำไว้กับ team suggestion ในไฟล์ 38
5. **สิทธิ์ของ role "หัวหน้า" — ออกแบบแล้วในรอบนี้**: เห็นเมนู "มอบหมายงาน" ได้เสมอ scope เฉพาะทีมเดียวที่สังกัด (`Team.supervisor_id`) ส่วนการ assign/reassign ขึ้นกับ Settings ต่อ Role Group (default เปิด) — ยังไม่มีสิทธิ์เข้าเมนู "รับเคส" (ไฟล์ 38) ในรอบนี้ ส่วนรายละเอียดเพิ่มเติม (เช่น สิทธิ์อนุมัติ/ตรวจงานอื่นๆนอกเหนือจากมอบหมายงาน) ยังเปิดไว้สำหรับออกแบบเพิ่มในอนาคตถ้ามี requirement ใหม่
6. **ช่องทางที่พนักงานคนเดิมรับ/ตอบคำขอ reassignment**: ฝั่ง UI ที่พนักงานใช้ตอบ "ยินยอม/ไม่ยินยอม" อาจต้องออกแบบร่วมกับไฟล์ 41 (Field Tracker Mobile) เพราะพนักงานใช้งานผ่านมือถือเป็นหลัก — รอบนี้ระบุไว้แค่ฝั่ง business logic/API ส่วน UI มือถือจริงรอออกแบบตอนทำไฟล์ 41
7. **ความถี่ของ scheduled job ตรวจ timeout**: ต้องกำหนดรายละเอียด implementation ว่าจะตรวจ `pending_reassignment.expires_at` ทุกกี่นาที เพื่อ balance ระหว่างความแม่นยำของเวลากับภาระระบบ
