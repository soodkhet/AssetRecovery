## 1. Summary

รวมการตั้งค่าพื้นฐานทั้งหมดที่โมดูล Finance/Accounting อื่นต้องอ้างอิง — รอบบิล/รอบจ่าย, สายการอนุมัติ, บัญชีธนาคารบริษัท, Tax Profile, Cost Center, รูปแบบเอกสาร, รูปแบบไฟล์โอนธนาคาร, Export format, สิทธิ์การเข้าถึงเฉพาะโมดูลนี้, และนโยบายล็อกรอบบัญชี

## 2. Purpose

เป็น "control panel" ของแอดมินการเงิน/บัญชี ที่ตั้งค่าเงื่อนไขกลางครั้งเดียว แล้วทุกโมดูล (15-37) ดึงไปใช้

## 3. In Scope

ทั้ง **13 sub-section** ตามที่ระบุใน §6 (§6.1 ถึง §6.13)

## 4. Out of Scope

- ตัวเลขจริงของรายการ (claim, payout, billing) — อยู่ในไฟล์โมดูลนั้นๆ
- การคำนวณภาษีเชิงสูตร (สรุปอีกรอบที่ไฟล์ 22)

## 5. Actors & Responsibilities

| Actor / Role | Responsibility | Scope |
|---|---|---|
| Superadmin only | ตั้งค่าทุก sub-section | Global |
| บริหาร (Executive) | อนุมัติการล็อกรอบ/ปลดล็อกหลังส่งมอบบัญชีแล้ว (§6.11) | Lock/Unlock approval |
| การเงิน, บัญชี | ดู settings เพื่ออ้างอิง — แก้ไขเองไม่ได้ | Read-only |

### 6.1 Billing/Payout Cycles (รอบบิลและรอบจ่าย)

กำหนดวันตัดรอบ (cut-off) และเงื่อนไขกำหนดชำระ/จ่าย แยกฝั่ง AR (รับ) และ AP (จ่าย)

| Field | Type | Required | Description |
|---|---|---|---|
| id | uuid | yes | — |
| name | string | yes | ชื่อรอบ (เช่น "AR รอบวางบิลหลัก") |
| type | enum | yes | `AR` (รอบวางบิลรับ) / `AP` (รอบจ่ายออก) |
| cutoff_rule_type | enum | yes | `fixed_dates` (วันที่คงที่ เช่น ทุกวันที่ 15 และ 30) / `month_end` (ทุกสิ้นเดือน) — **มติ PO U146: ตัด `custom_text`** (ข้อความอิสระคำนวณวันตัดรอบไม่ได้ · ค่าเดิมแปลงเป็นวันที่ที่อ่านได้จากข้อความ + "สิ้นเดือน" = 31 หรือสิ้นเดือน) |
| cutoff_dates | array of integer \| null | — | ใช้เมื่อ `cutoff_rule_type = fixed_dates` — รายการวันที่ในเดือน เช่น `[15, 30]` (วันที่เกินจำนวนวันในเดือน = วันสุดท้ายของเดือนนั้น) |
| legacy_cutoff_text | string \| null | no | ข้อความกติกาแบบอิสระเดิมก่อนมติ U146 — อ้างอิงเท่านั้น ไม่มีผล · รอบใหม่ = null |
| due_rule | string | yes | เงื่อนไขกำหนดชำระ/จ่าย (เช่น "Net 30 Days", "วันที่ 5 ของเดือนถัดไป") |
| scope_kind | enum `cycle_scope_kind` | yes | ขอบเขตจริง (มติ PO U133) — AR: `all_companies` (บริษัทไฟแนนซ์ทุกราย) / `selected_companies` (เลือกรายบริษัท ≥ 1) · AP: `all_teams` / `inhouse` / `outsource` · CHECK เข้าคู่ชนิดรอบ |
| company_ids | array of uuid | เฉพาะ `selected_companies` | บริษัทที่ใช้รอบนี้ (ตาราง `billing_cycle_companies`) |
| legacy_scope_note | string \| null | no | ข้อความ "ใช้กับ" แบบอิสระเดิมก่อนมติ U133 — อ้างอิงเท่านั้น ไม่มีผล · รอบใหม่ = null |

กติกาขอบเขต (มติ PO U133):
- **ห้ามซ้อน** กับรอบชนิดเดียวกันที่ยังใช้งาน: "ทุกบริษัท" ซ้อนรอบบิลทุกรอบ · บริษัทเดียวกันอยู่ได้รอบบิลเดียว · "ทุกทีม" ซ้อนรอบจ่ายทุกรอบ · ฝั่ง In-house/Outsource อยู่ได้รอบเดียวต่อฝั่ง ⇒ `CYCLE_SCOPE_OVERLAP` (409) · ตรวจภายใต้ lock ต่อองค์กร+ชนิด (สร้างพร้อมกันได้รอบเดียว) · รอบที่ปิดใช้งานไม่นับ
- **มีผลจริง**: สร้างรอบวางบิล (`19` §9.1) ⇒ ระบบเลือกรอบบิลที่ครอบบริษัทนั้นให้อัตโนมัติ (รอบที่ระบุบริษัทชนะ "ทุกบริษัท") ใช้คำนวณวันครบกำหนด · สร้างรอบจ่าย (`17` §8) ⇒ เลือกรอบจ่ายที่ครอบฝั่งนั้นให้ · คำนวณกำหนดจ่าย = เงื่อนไขกำหนดชำระของรอบนับจากวันตัดรอบ (snapshot `payout_batches.pay_due_date`) · ผู้ใช้เปลี่ยนเป็น "ไม่ใช้รอบ" ได้ · ส่งรอบที่ไม่ครอบ = `CYCLE_SCOPE_MISMATCH`
- **แหล่งเดียวของวันตัดรอบ + เครดิตเทอม (มติ PO U146)**: รอบบิลกำหนดทั้งวันตัดรอบและวันครบกำหนดของบริษัทที่อยู่ในรอบ — หน้าบริษัทไฟแนนซ์เลือก "รอบบิลที่ใช้" (เพิ่ม/ถอดบริษัทในรายชื่อของรอบ · `10` §7.1) แทนช่องวันตัดรอบ/เครดิตเทอมของบริษัทเดิม · หน้าสร้างรอบวางบิล/รอบจ่ายเสนอ**วันตัดรอบล่าสุดที่ไม่เกินวันนี้**ตามกติกาของรอบ (แก้ได้) · บริษัทไม่มีรอบบิล = สร้างรอบวางบิลไม่ได้ (`BILLING_CYCLE_NOT_SET`) · `net_days` รับ 0 ได้ (ครบกำหนดวันตัดรอบ)
- ข้อมูลเดิม (ก่อน U133): AR = ทุกบริษัท · AP = ฝั่งที่ข้อความระบุชัดเพียงฝั่งเดียว ไม่งั้นทุกทีม · ข้อความเดิมเก็บใน `legacy_scope_note` + audit before/after ของการแก้ครั้งถัดไป — รอบเดิมที่ซ้อนกันอยู่ต้องแก้ขอบเขตให้ไม่ซ้อนก่อนบันทึกครั้งถัดไป

#### 6.4.1 หมายเหตุสำคัญ — เงินเดือนพนักงาน inhouse ไม่อยู่ในขอบเขตของ AssetRecovery

พนักงาน inhouse เป็นพนักงานประจำ ได้รับเงินเดือนตามมาตรา 40(1) ซึ่งกฎหมายกำหนดให้คำนวณภาษีหัก ณ ที่จ่ายแบบ**ขั้นบันได** (เทียบเงินได้พึงประเมินทั้งปี หักค่าใช้จ่าย/ค่าลดหย่อน แล้วหารเฉลี่ยเป็นรายเดือน) ไม่ใช่อัตราคงที่แบบ outsource — **ยืนยันแล้วว่าเรื่องเงินเดือน inhouse (ภ.ง.ด.1, ประกันสังคม, กองทุนสำรองเลี้ยงชีพ ฯลฯ) ไม่อยู่ในขอบเขตของระบบนี้เลย** จัดการแยกในระบบ/บริการ payroll อื่นโดยเฉพาะ (เช่น ผ่านสำนักงานบัญชีหรือโปรแกรมเงินเดือนแยก) — Tax Profile ในไฟล์นี้ใช้กับ **ค่าตอบแทนจากการทำเคส** เท่านั้น (ค่าน้ำมัน/เบี้ยเลี้ยง/คอมมิชชั่นตามไฟล์ 11) ไม่ครอบคลุมเงินเดือนประจำ

> **มติ PO 05/10/2569 (UAT U33)**: **ค่าตอบแทนจากการทำเคส**ที่ระบบจ่าย (ไม่ใช่เงินเดือนประจำ) อาจถูกจัดเป็นเงินได้ 40(1) / 40(2) / 40(8) ตามคำแนะนำของสำนักงานบัญชี — ตั้งได้ที่ §6.4.2 (โหมดแยกตามประเภททีม เลือกต่อ inhouse / outsource) · 40(1) ใช้อัตราต่อคนที่สำนักงานบัญชีคำนวณให้ (ระบบไม่คำนวณขั้นบันไดเอง — Hybrid Boundary) + ยื่น ภ.ง.ด.1 · เงินเดือน ประกันสังคม กองทุนสำรองเลี้ยงชีพ ยังอยู่นอกขอบเขตตามเดิม

#### 6.4.3 Tax Profile ค่าเริ่มต้นตามประเภทผู้รับ (มติ PO 06/10/2569 — U121)

ค่าตั้ง **4 ช่อง** = ฝั่งผู้รับ (inhouse/outsource — ตามทีม/role ของผู้รับ แบบเดียวกับการแยกฝั่งรอบจ่าย) × ชนิดผู้รับ (บุคคลธรรมดา/นิติบุคคล — `payee_profiles.payee_type`) · แต่ละช่องผูก Tax Profile ที่ใช้งานอยู่ได้ 0–1 ตัว (**ว่างได้**) · เก็บที่ `tax_profile_default_history` (`02` v4.48) แบบ **insert-only** — บันทึก = เพิ่มชุดใหม่ (ประวัติไม่ถูกแก้/ลบ) · ชุดที่บันทึกล่าสุด **มีผลทันที** กับคิวอนุมัติ/ไฟล์ค้างจ่าย/รอบจ่ายที่สร้างหลังบันทึก

- **ลำดับ resolve อัตรา 40(8)/นิติบุคคล** (`18` §6.3 · `22` §6.9): Tax Profile **รายคน** (`payee_profiles.tax_profile_id` — ข้อยกเว้น/override) → **ค่าเริ่มต้นตามประเภท** (นับเป็นฝั่ง payee ⇒ "Payee ชนะ Plan" คงเดิม · ไม่เตือน) → อัตราของแผน (fallback + `WHT_RATE_FALLBACK_TO_PLAN` เดิม) → **ไม่มีเลย = บล็อก**: คิวอนุมัติแสดงคำเตือนต่อแถว (ไม่ล้มทั้งหน้า) · สร้างรอบจ่ายไม่ได้ `WHT_RATE_MISSING` พร้อมรายชื่อ (ห้ามเดาอัตรา)
- รายการที่**ไม่อยู่ในฐาน WHT** (§6.4.2) ไม่ resolve อัตราเลย — ผู้รับที่ไม่มีอัตราก็จ่ายรายการนอกฐานได้ตามปกติ
- อัตรา 40(1)/40(2) ต่อคน (`wht_40_2_pct`) **คงเดิม** — ค่าเริ่มต้นตามประเภทใช้กับเงินได้ที่ใช้ Tax Profile เท่านั้น · นิติบุคคลยื่น ภ.ง.ด.53 เสมอ (ไม่ขึ้นกับ `filing_form` ของ profile)
- Snapshot: รอบจ่ายเก็บ Tax Profile ที่ใช้จริงต่อรายการที่ `payout_batch_items.tax_profile_id` (รวมกรณีมาจากค่าเริ่มต้น) + id ชุดค่าเริ่มต้นที่ `payout_batches.tax_profile_default_id` ⇒ แก้ค่าตั้งภายหลังไม่กระทบรอบเดิม
- สิทธิ์: อ่าน = `view_master_data` · แก้ = `manage_tax_profiles` (**ล็อก Superadmin** — แนวเดียวกับ Tax Profile) · **เหตุผลบังคับ** + audit before/after (`target_type = tax_profile_default_history`)
- อ้าง Tax Profile ที่ไม่มี/ปิดใช้งาน/ข้ามองค์กร ⇒ `TAX_PROFILE_NOT_FOUND` · ปิดใช้งาน Tax Profile ที่เป็นค่าเริ่มต้นของชุดที่มีผล ⇒ `TAX_PROFILE_IN_USE` (เปลี่ยนค่าเริ่มต้นก่อน)
- ค่าเริ่มต้นตอนติดตั้ง (seed): outsource บุคคลธรรมดา → 3% ก่อน VAT เกณฑ์ ฿1,000 ภ.ง.ด.3 · outsource นิติบุคคล → 3% ภ.ง.ด.53 · ช่อง inhouse ว่าง (ใช้อัตรา 40(1)/40(2) ต่อคนตามค่าตั้ง §6.4.2)
- หน้าจอ: กล่อง "Tax Profile ค่าเริ่มต้นตามประเภทผู้รับ" ในแท็บ Tax Profile (ใต้ตาราง profile) + กล่องคำอธิบาย (§7.1) — mockup `settings.html` → `renderSettingsTax`
- API: `GET /api/settings/tax-profile-defaults` (ชุดที่มีผล + ประวัติ) · `POST` (ชุดใหม่ + `reason`)

### 6.5 VAT Rate Setting (อัตราภาษีมูลค่าเพิ่ม) 🔶 สำคัญมาก — ติดตามใกล้ชิด

AssetRecovery จด VAT (ยืนยันจาก Product Owner) — ต้องตั้งค่าอัตรา VAT แบบมี **effective date versioning** ไม่ hardcode ค่าตายตัว เพราะอัตรา VAT ของไทยเป็นอัตราลดพิเศษที่ต้องต่ออายุเป็นระยะ

**สถานะ ณ วันที่เขียนสเปคนี้ (29 มิ.ย. 2569)**: อัตราปัจจุบันคือ **7%** ตามพระราชกฤษฎีกาที่ขยายเวลาถึง 30 กันยายน 2569 — อัตราตามกฎหมายจริงคือ 10% และมีความเป็นไปได้ที่จะกลับไปใช้ 10% ตั้งแต่ 1 ตุลาคม 2569 หากไม่มีการขยายเวลาลดอัตราต่อ (ต้องติดตามประกาศกรมสรรพากร/ราชกิจจานุเบกษาใกล้ช่วงนั้น)

| Field | Type | Required | Description |
|---|---|---|---|
| id | uuid | yes | — |
| rate | decimal | yes | อัตรา VAT เป็น % (เช่น 7.00) |
| effective_from | date | yes | วันที่เริ่มมีผล |
| effective_to | date \| null | — | วันสิ้นสุด — `null` แปลว่ายังใช้อยู่จนกว่าจะมีรายการใหม่ |

- ระบบใช้ค่านี้คำนวณ VAT ของ Revenue ทุกรายการ (ไฟล์ 19) โดยอ้างอิงวันที่เกิดรายได้ (`revenue_date`) เทียบกับช่วง `effective_from`/`effective_to`
- ห้ามมีช่วงเวลาทับกัน (validation บังคับ)
- แก้ไข/เพิ่มอัตราใหม่ต้อง audit + reason เสมอ (กระทบยอดภาษีทั้งระบบ)

- รีเซ็ตรายปี: ปีของเอกสารตรงกับตัวนับ = นับต่อ · ปีอื่น (ขึ้นปีใหม่/ลงวันที่ย้อนปี) = ต่อจากเลขสูงสุดที่มีจริงของปีนั้น · เอกสารย้อนปีไม่ดึงตัวนับปีปัจจุบันถอยหลัง
- **เอกสารภาษี (INV, WHT) ล็อกรูปแบบหลังออกฉบับแรก** (`NUMBERING_FORMAT_LOCKED`) และตั้งเลขถัดไปเองไม่ได้ — ตั้งรูปแบบให้เรียบร้อยก่อนออกฉบับแรก (คำถามสำนักงานบัญชี C1)

### 6.14 SLA Alert Threshold (เกณฑ์ SLA งานติดตาม) — มติ PO 15/08/2569 (D18)

เกณฑ์เวลาที่ใช้ตัดสินว่าเคส "เกินกำหนด" ในรายงาน O2 (ประสิทธิภาพทีม/SLA) และ O4 (เคสค้างเกิน SLA) ของไฟล์ 96 — ไฟล์ 96 §6-O2/O4 อ้าง `slaAlertHours` ว่าอยู่ใน "Finance Settings (ไฟล์ 03)" แต่ไฟล์ 03 ไม่เคยนิยามค่านี้ (§18 ระบุเองว่าตัวเลข SLA ยังไม่ตกลง) ⇒ PO เคาะให้ตั้งค่าที่นี่

| Field | Type | Required | Description |
|---|---|---|---|
| sla_alert_hours | integer | yes | เกณฑ์ SLA เป็นชั่วโมง **นับจาก `cases.created_at`** (วันที่รับเคสเข้าระบบ) — ค่าเริ่มต้น **72 (3 วัน)** · ต้อง > 0 และไม่เกิน 8,760 (1 ปี) |

- **1 record ต่อองค์กร** — เก็บที่ตาราง `assignment_policy_settings` (ไฟล์ 02 · ตารางค่าตั้งของงานมอบหมายตามไฟล์ 40 §6.4) ⇒ แท็บนี้แก้เฉพาะคอลัมน์ `sla_alert_hours` ไม่แตะค่าตั้ง assign/reassign ของไฟล์ 40
- **ขอบเขตการใช้งาน: รายงานเท่านั้น** — เกินเกณฑ์แล้วระบบไม่บล็อกงาน ไม่มอบหมายใหม่อัตโนมัติ ไม่มีค่าปรับ (คำถาม "เกิดอะไรขึ้นเมื่อ breach" ยังค้างที่ `DECISIONS-NEEDED.md` §3.2)
- แก้ไขต้องมี `reason` เหมือนทุกแท็บในไฟล์นี้ (ตารางนี้อยู่หมวด permission ของนโยบาย audit) และมีผลกับรายงานรอบถัดไปทันที (แคชรายชั่วโมงตามไฟล์ 96 §8 หรือกดรีเฟรชที่หน้ารายงาน)

### 6.15 ปฏิทินวันหยุด (Public Holidays) — มติ PO 06/10/2569 (UAT U93)

วันหยุดราชการและวันหยุดของบริษัทที่ระบบใช้คิด **วันทำการ** — ธุรการ/บัญชี/การเงินกรอกปีละครั้ง (ระบบไม่ seed วันหยุดจริง · หน้าว่างแสดงคำแนะนำให้นำเข้าทั้งปี)

| Field | Type | Required | Description |
|---|---|---|---|
| holiday_date | date | yes | วันหยุด (date-only) — วันเดียวกันมีได้รายการเดียวที่ยังไม่ลบ (`DUPLICATE_HOLIDAY_DATE`) |
| name | string | yes | ชื่อวันหยุด เช่น "วันปิยมหาราช" (≤ 120 ตัวอักษร) |

- **เพิ่มทีละวัน** หรือ **นำเข้าหลายวัน**: วางรายการ/เลือกไฟล์ CSV บรรทัดละ `YYYY-MM-DD,ชื่อ` (คั่น comma หรือ tab · ปี ค.ศ. หรือ พ.ศ. ก็ได้ · ข้ามหัวตาราง/บรรทัดว่าง/`#`) — ตรวจรายบรรทัดก่อนส่ง · ครั้งละ ≤ 100 วัน · วันที่มีอยู่แล้ว**ถูกข้าม** (ไม่ปฏิเสธทั้งชุด)
- **ลบ = soft delete** พร้อมเหตุผล — ลบแล้วเพิ่มวันเดิมใหม่ได้ · ไม่มีการแก้ไข (ลบแล้วเพิ่มใหม่)
- แสดงรายการตาม **ปี พ.ศ.** (ตัวกรองปี: ปีที่มีข้อมูล + ปีนี้ + ปีหน้า + ทุกปี) — คอลัมน์ วันที่ (พ.ศ.) / วัน / ชื่อ / ผู้บันทึก
- **ผลต่อระบบ**: กำหนดยื่น ภ.ง.ด. (`33` §7.2) ที่ตรงวันหยุดในปฏิทินนี้หรือเสาร์/อาทิตย์ ⇒ เลื่อนเป็นวันทำการถัดไป · ทุกการเพิ่ม/ลบ/นำเข้า **คิดกำหนดยื่นของรอบที่ยังไม่ยื่นใหม่ทันที** ในทรานแซกชันเดียวกัน (แบบที่ §6.4.2 ทำตอนเปลี่ยนวิธียื่น) และลง audit ของรอบที่เปลี่ยน
- กำหนดอื่นในระบบ (วันครบกำหนดชำระของรอบบิล §6.1, เกณฑ์ SLA §6.14, เงินทดรองเกินกำหนด) **ยังนับวันปฏิทิน** — ไม่ใช่กำหนดยื่นภาษี (มติ U93 ใช้กับกำหนดยื่นภาษีเท่านั้น)
- สิทธิ์: `manage_holidays` — ธุรการ/บัญชี/การเงิน = manage · บริหาร = view · Superadmin โดยนิยาม · **ไม่ใช่ "✅ only"** (มอบ role อื่นได้) · ผู้ใช้กลุ่มปฏิบัติการเข้าหน้าตั้งค่าบัญชี/การเงินได้ผ่านสิทธิ์นี้และเห็นเฉพาะแท็บนี้
- ทุกการเพิ่ม/ลบต้องมี `reason` (กระทบกำหนดยื่นภาษี — หมวด tax ของนโยบาย audit)

### 7.1 คำอธิบายในหน้าจอ (มติ PO 06/10/2569 U108)

ทุกค่าตั้งที่กระทบเงิน/บัญชี/ภาษี/เอกสาร ต้องมีกล่องคำอธิบายแบบพับได้ (ไอคอน ⓘ) ภาษาไทยที่คนที่ไม่ใช่นักบัญชีอ่านเข้าใจ ตอบ 4 คำถาม:

1. **คืออะไร / ใช้ทำอะไร**
2. **ผลของแต่ละตัวเลือก**
3. **ตัวอย่างตัวเลข** (เฉพาะค่าที่กระทบเงิน) — คำนวณด้วย **สูตรจริงของระบบ** (`22` ผ่าน pure module) จากค่าที่กำลังเลือกในฟอร์ม และอัปเดตสดทุกครั้งที่แก้ค่า · ห้าม hardcode ผลลัพธ์ · อัตรา VAT ในตัวอย่างมาจาก `vat_rate_history` ที่มีผลวันนี้ (ไม่มี = แจ้งว่ายังไม่ตั้ง)
4. **ใครแก้ได้ + มีผลเมื่อไร** (ทันที / รอบจ่ายถัดไป / ฉบับถัดไป / ล็อกหลังออกฉบับแรก / ตามวันที่มีผล)

ข้อความที่ผู้ใช้เห็นห้ามมีเลขอ้างอิงสเปค (Rule 05) · component กลาง `<SettingHelp>` + ข้อความรวมที่ `lib/settings/help/*`

**ป้าย "รอนักบัญชียืนยัน" (มติ PO 07/10/2569 U140)**: ค่าตั้งที่ระบบใช้ค่าแนะนำไปก่อนระหว่างรอคำตอบนักบัญชี (คำถาม Q1–Q18 · ข้อมูลตั้งต้น A/C/F · มติเชิงบัญชี A1–A9 · U128) แสดงป้ายเหนือกล่องคำอธิบายของค่าตั้งนั้น พร้อมสิ่งที่ขอให้ยืนยัน · ทะเบียนรายการ `lib/settings/assumptions.ts` (ผูกด้วยฟิลด์ `assumption` ของเนื้อหากล่อง) — ประเภทเงินได้ · ฐาน WHT · ใบ 0% · รูปแบบ 50 ทวิ · เกณฑ์ขั้นต่ำ/อัตรา (Tax Profile) · กำหนดยื่น · เงื่อนไขภาษีออกให้ · ปฏิทินวันหยุด · การปัดเศษ VAT · รายการบนใบกำกับ · รูปแบบเลขใบกำกับ · ใบสำคัญจ่าย · ชุดเอกสารบัญชี (รวมไฟล์ 05 ตามเดือนที่จ่าย) · ศูนย์ต้นทุน · ไฟล์โอนธนาคาร · ค่าที่พักไม่ใช่นามบริษัท · ปรับปรุงหลังปิดงวด · ภาษีที่ลูกค้าหัก · ผู้ถือ `manage_accountant_questions` กด "ยืนยันแล้ว" + เหตุผลบังคับ ⇒ บันทึก `setting_assumption_confirmations` (insert-only) + audit แล้วป้ายหาย (`GET /api/settings/assumptions` อ่านด้วย `view_master_data` · `POST /api/settings/assumptions/:key/confirm`)

## 8. Workflow / Lifecycle

ส่วนใหญ่เป็น static configuration ไม่มี state machine ของตัวเอง ยกเว้น §6.8 (Bank File Format) ที่มี `test_status` ต้องผ่านการทดสอบก่อนใช้งานจริง:

`pending → ทดสอบไฟล์ตัวอย่าง → passed/failed → (ถ้า failed) แก้ column_mapping → ทดสอบใหม่`

## 9. Security / Control Rules

- แก้ไข Tax Profile (§6.4) ต้อง audit + reason เสมอ (กระทบยอดภาษีทุกรายการที่ใช้ profile นั้น)
- แก้ไข VAT Rate (§6.5) ต้อง audit + reason เสมอ — ห้ามมีช่วงเวลาทับกัน (validation บังคับ)
- แก้ไข Period Lock Policy (§6.11) เองทำได้เฉพาะ Superadmin — Admin ทั่วไปดูได้อย่างเดียว เพราะเป็น policy ระดับองค์กร
- บัญชีธนาคาร (§6.3) ที่มีรายการเงินผูกอยู่แล้ว ห้ามลบ — แก้ไขได้แต่ต้อง audit

## 16. การตัดสินใจที่เกี่ยวข้อง (Decisions)

- **13 sub-section ครบ** (§6.1-6.13) — แก้ไขจำนวนที่เขียนผิดใน §3 เดิม (เคยเขียนว่า 10) ให้ตรงกับ README แล้ว · **+§6.14 เกณฑ์ SLA** เพิ่มตามมติ PO 15/08/2569 (D18) รวมเป็น 14 sub-section
- **เกณฑ์ SLA เป็นค่าตั้งระดับองค์กร ค่าเริ่มต้น 72 ชั่วโมง และใช้กับรายงาน O2/O4 เท่านั้น** — ไม่บล็อกงาน ไม่ auto-reassign ไม่มีค่าปรับ (§6.14 · มติ PO 15/08/2569)
- **WHT rate มาตรฐาน 3%** สำหรับค่าจ้างทำของ/ค่าบริการ (มาตรา 40(7)/40(8)) — ตั้งเป็นค่าเริ่มต้นได้แต่ต้องเป็นฟิลด์ตั้งค่า ไม่ hardcode (§6.4) 🔶
- **เงินเดือนพนักงาน inhouse ไม่อยู่ในขอบเขตของระบบนี้เลย** — Tax Profile ใช้กับค่าตอบแทนจากการทำเคสเท่านั้น (§6.4.1)
- **VAT Rate ต้องมี effective date versioning เสมอ ห้าม hardcode** เพราะอัตราไทยเป็นอัตราลดพิเศษที่ต้องต่ออายุเป็นระยะ (§6.5) 🔶
- **Tax Invoice Numbering Format เลือกครั้งแรกแล้วไม่ควรเปลี่ยน** เพราะกระทบความต่อเนื่องของเลขเอกสารตามกฎหมาย (§6.12)
- **Period Lock Policy 3 สถานะ** (`collecting`/`sent_to_accountant`/`locked`) กำหนดสิทธิ์แก้ไขต่างกันชัดเจน — เป็น policy หลักที่ไฟล์ 20/30 ต้อง enforce (§6.11)
- **Bank File Format ต้อง `test_status = passed` ก่อนใช้ตัดโอนเงินจริงเสมอ** (§6.8, §10 BANK_FILE_NOT_TESTED)
