## 1. Summary
แอปสำหรับพนักงานติดตามทรัพย์ (Field Agent) ใช้รับงาน, จัดวันลงพื้นที่, เช็คอิน/บันทึกหลักฐาน, ปิดงาน, และเบิกค่าใช้จ่าย — เป็นจุดสุดท้ายของ pipeline งานสนาม ต่อจากไฟล์ 40 (มอบหมายงาน) และส่งผลลัพธ์กลับไปไฟล์ 38 (ผ่าน recycle flow ถ้าไม่สำเร็จ) และไฟล์ 43 (ผลการติดตาม)

## 2. Purpose
ให้พนักงานภาคสนามจัดการงานตัวเองได้ครบในที่เดียว: ตั้งแต่กดรับงาน → จัดลำดับวันลงพื้นที่ → เก็บหลักฐานการปฏิบัติงาน → ปิดงาน → ดูค่าตอบแทน/เบิกค่าใช้จ่าย โดยไม่ต้องพึ่งเครื่องมืออื่นนอกระบบ

## 3. Scope

### 3.1 In Scope
- 2 เวอร์ชันแยกไฟล์กันชัดเจน: **Mobile-first** (งานสนามทั้งหมด) และ **Desktop** (Layout เดียวกันทุกฟีเจอร์ ปรับแค่ขนาดจอ — ไม่ตัดฟีเจอร์ฮาร์ดแวร์ออก)
- สถานะเคส 4 กลุ่มหลัก: รอรับงาน → รับงานแล้ว (รอจัดวัน) → กำลังติดตาม (จัดวันแล้ว) → จบงาน (สำเร็จ/ไม่สำเร็จ)
- ปฏิทินจัดวันที่แบบ Google-Calendar-style พร้อมมุมมอง "ของฉัน" / "ทีม"
- ฟอร์มปิดงานพร้อมหลักฐาน (เช็คอินหลายจุด, รูปถ่ายหลายไฟล์, วิดีโอหลายไฟล์, เสียงไม่บังคับ) และระบบบันทึก Draft
- ตอบรับ/ปฏิเสธคำขอเปลี่ยนผู้รับผิดชอบ (`pending_reassignment` จากไฟล์ 40)
- เบิกค่าใช้จ่าย แยก "ผูกกับเคส" (ระบบสร้างอัตโนมัติ) กับ "เบิกแยก" (ที่พัก — ผู้ใช้กรอกเอง)
- สรุปรายได้ (คอมมิชชั่น) และ Dashboard ภาพรวม

### 3.2 Out of Scope (ยกไปเฟส/เอกสารอื่น)
- **Map/จัดเส้นทางอัตโนมัติด้วย GPS routing** — ตัดออกจากเฟสแรกทั้งหมด (ดู Open Items #1)
- **Offline Support** — ต้องมีอินเทอร์เน็ตเสมอ ไม่มี sync queue/conflict resolution ในเฟสนี้ (ดู Open Items #2)
- **โมดูลคลังสินค้า** — ✅ ออกแบบเสร็จสมบูรณ์แล้ว (ดูไฟล์ 44 และ warehouse.html) — ดู Open Items #3
- **เอกสารสัญญา/อัปโหลดไฟล์ใหญ่จากคอม** — เป็น use case ของ Desktop แต่ไม่ได้ผูกกับ flow งานสนามในไฟล์นี้ (ดู Open Items #4)
- **Pinpoint Geocoding API integration จริง** — รายละเอียดเทคนิคอยู่ในเอกสารทดสอบแยก ยังไม่ implement จริงในเฟสนี้

## 5. Menu & Navigation

### 5.1 Mobile — Bottom Nav (4 รายการ) + Top Bar
- **Top Bar**: โลโก้ซ้าย (กดแล้วกลับหน้าแรกเสมอ) + ปุ่มแฮมเบอร์เกอร์ขวา
- **Bottom Nav 4 ปุ่ม**: รอรับงาน → รับงานแล้ว → กำลังติดตาม → จบงาน (เรียงตาม flow การทำงานจริง ไม่ใช่ "หน้าแรก" เป็นปุ่มแรกแบบแอปทั่วไป เพราะพนักงานเข้าแอปเพื่อเช็คงานเป็นหลัก)
- แต่ละปุ่มที่มีงานค้างมี badge ตัวเลขสีแดง (รอรับงาน, รับงานแล้ว) หรือสีม่วง (กำลังติดตาม — เฉพาะตอนมี `pending_reassignment` ค้างตอบ ดู §6.7)
- **เมนูแฮมเบอร์เกอร์** (เปิดจาก top bar) รวมทุกเมนูแบ่ง 2 หมวด:
  - **งานของฉัน**: หน้าแรก (Dashboard), รอรับงาน, รับงานแล้ว, กำลังติดตาม, จบงาน
  - **การเงิน**: เบิกค่าใช้จ่าย, สรุปรายได้
  - **บัญชี**: ออกจากระบบ

### 5.2 Desktop — Sidebar ถาวร (Fixed)
- **Sidebar กว้าง 260px ติดซ้ายตลอด** ใช้ CSS `position: fixed` (ไม่ใช่ `sticky` — เพื่อล็อกตำแหน่งแน่นอนไม่ขึ้นกับ parent overflow context) มีโลโก้บนสุด, รายการเมนู, ข้อมูลผู้ใช้ด้านล่างสุด
- รวมทุกเมนูไว้ใน sidebar เดียว ไม่มี popup/modal สำหรับเมนูหลัก — **"เบิกค่าใช้จ่าย" และ "สรุปรายได้" เป็นหน้าเพจเต็มเหมือนเมนูอื่น ไม่ใช่ modal**
- หมวดหมู่เดียวกับ mobile: งานของฉัน (5 รายการ) / การเงิน (2 รายการ)
- เนื้อหาหลักอยู่ฝั่งขวาด้วย `margin-left: 260px` เต็มความกว้างที่เหลือ
- List เคสทุกหน้าแสดงเป็น**แนวตั้งคอลัมน์เดียวเต็มความกว้าง** ไม่แบ่งเป็น grid หลายคอลัมน์ (ต่างจาก draft แรกที่เคยลองทำ multi-column แล้วถูกขอให้เปลี่ยนกลับ)

## 6. Data Requirements

### 6.1 Case Assignment Status (รับช่วงจากไฟล์ 40)

|---|---|---|---|

### 6.2 Address Structure (3 ที่อยู่ — รับมาจากไฟล์ 38 §6.1.2)
แต่ละที่อยู่มีโครงสร้างเดียวกัน object `{ label, detail, subdistrict, district, province, postcode, lat, lng }`:
|Address Type|Label|Source|
|---|---|---|
|`current`|ที่อยู่ปัจจุบัน|ใช้ routing/แสดงหลักในการ์ดเคสทุกที่|
|`work`|ที่ทำงาน|อาจเป็น `-` ทั้ง object ถ้าไม่มีข้อมูล|
|`id_card`|ที่อยู่ตามบัตรประชาชน|ใช้เทียบกับที่อยู่ปัจจุบันกรณีลูกหนี้ย้ายที่อยู่|

แต่ละที่อยู่มีปุ่ม **"เปิด Google Maps"** แยกอิสระ — ถ้ามี `lat`/`lng` ใช้ `https://www.google.com/maps?q={lat},{lng}` (แม่นยำกว่า) ถ้าไม่มีพิกัด fallback เป็น URL search ด้วยที่อยู่เต็มแบบ string (`https://www.google.com/maps/search/{encoded address}`)

### 6.4 Evidence (หลักฐานการปิดงาน)
โครงสร้าง `evidence` object เก็บแยกตามประเภท ไม่ใช่ boolean flag เดี่ยว:
|Field|Type|Description|
|---|---|---|
|checkins|array|รายการจุดเช็คอิน — แต่ละจุด `{ label, time, lat, lng }` พิกัดได้จาก device GPS ปัจจุบันเท่านั้น **ปักหมุดมือไม่ได้** — เพิ่มได้หลายจุด (เผื่อไปบ้านไม่เจอ ไปที่ทำงานต่อ)|
|photos|array|รายการไฟล์รูปถ่าย — เพิ่มได้หลายไฟล์ มี thumbnail preview|
|videos|array|รายการไฟล์วิดีโอ — เพิ่มได้หลายไฟล์ มี thumbnail preview|
|product|boolean|รูปสินค้ายืนยัน — บังคับเฉพาะ outcome = สำเร็จ|
|audio|boolean|เสียงบันทึกการสนทนา — ไม่บังคับทุก outcome|

> แต่ละจุดเช็คอินแสดงเป็น **static map preview** (ภาพแผนที่ขนาดเล็ก ดูอย่างเดียว แก้ไขไม่ได้) พร้อมลิงก์เปิด Google Maps จริงถ้าต้องการดูเต็ม

### 6.4.1 Travel Origin (จุดเริ่มเดินทาง — สำหรับคำนวณค่าน้ำมัน PER_KM)
|Field|Type|Description|
|---|---|---|
|case_id|uuid|เคสที่จุดนี้ผูกอยู่ด้วย (1 เคส มีได้แค่ 1 จุดเริ่มเดินทาง)|
|lat / lng|decimal|พิกัดจุดเริ่มเดินทาง|
|source|enum|`gps_auto` (ค่าเริ่มต้นจาก device GPS ตอนกดปุ่ม "เริ่มเดินทาง") / `manual_adjusted` (พนักงานลากปรับตำแหน่งบนแผนที่เอง)|
|set_at|timestamptz|เวลาที่กดปุ่ม "เริ่มเดินทาง"|

> **สำคัญ — `travel_origin` เป็นข้อมูลคนละชุดกับ `evidence.checkins`** ห้ามปนกัน:
> - `evidence.checkins` คือ**หลักฐาน**ว่าพนักงานไปถึงสถานที่จริง ต้องเป็น GPS จริงเท่านั้น แก้ไขไม่ได้ (ล็อกตลอด รวมถึงในโหมด `needs_revision` ตาม §10.1)
> - `travel_origin` คือ**จุดอ้างอิงสำหรับคำนวณเงิน**เท่านั้น ไม่ใช่หลักฐานว่าไปที่ไหน — ดึง GPS จริงมาเป็นค่าเริ่มต้น**อัตโนมัติทันทีที่กดปุ่ม "เริ่มงาน"** ของเคสนั้น (ไม่ต้องกดปุ่มแยกอีกขั้น) แต่**ปรับตำแหน่งบนแผนที่ได้อิสระ**เสมอ (กันกรณี GPS ตอนกดเริ่มงานไม่ตรงจุดออกเดินทางจริง)
> - **แต่ละเคสเริ่มอิสระ ไม่ auto-fill จากจุดจบของเคสก่อนหน้า** แม้จะเป็นเคสที่ 2, 3, 4 ของวันก็ตาม — กดปุ่ม "เริ่มงาน" ของเคสใหม่ ดึง GPS ปัจจุบัน ณ ขณะนั้นเสมอ ไม่เกี่ยวกับเคสอื่น

### 6.4.2 Distance Calculation (คำนวณระยะทางสำหรับค่าน้ำมัน PER_KM)
- คำนวณเฉพาะทีมที่ Compensation Template ตั้ง Fuel Rule เป็นโหมด `PER_KM` เท่านั้น (ทีมที่ใช้ `DAILY_FLAT` ไม่ต้องคำนวณระยะทาง — ดูไฟล์ 11 §7.1)
- **ลำดับจุดคำนวณ**: `travel_origin → evidence.checkins[1] → evidence.checkins[2] → ... → evidence.checkins[n]` ตามลำดับเวลาที่กดเช็คอินจริง (ไม่ใช่แค่จุดเริ่มถึงจุดไกลสุด) — ระยะทางรวมคือผลรวมระยะทางของทุกช่วงต่อกัน
- **Engine คำนวณระยะทางจริง (เฟสแรก)**: **Google Maps Distance Matrix API** — ส่งพิกัดคู่ต่อเนื่องกันไปคำนวณระยะทางตามถนนจริง (ไม่ใช่ Haversine เส้นตรง) — Pinpoint Route/Distance Matrix เก็บไว้พิจารณาเปลี่ยนเป็น default ในเฟสถัดไป ยังไม่ใช้ในรอบนี้
- เรียก API คำนวณตอน `submit_close_case`/`resubmit_close_case` เท่านั้น (ไม่คำนวณ realtime ทุกครั้งที่เพิ่มจุดเช็คอิน เพื่อลดจำนวน API call)
- **ยอดจ่ายค่าน้ำมันต่อเคส** = `MIN(ระยะทางจริงที่คำนวณได้ × rate_per_km, max_per_case)` ถ้า Compensation Template ตั้งค่า `max_per_case` ไว้ (ไม่ใช่ null/0) — ถ้าไม่ได้ตั้งค่าเพดานไว้ จ่ายตามระยะทางจริง × rate เต็มจำนวน ไม่มีเพดาน

### 6.5 Close-Case Draft (บันทึกฟอร์มปิดงานแบบไม่ครบ)
|Field|Type|Description|
|---|---|---|
|case_id|uuid|เคสที่กำลังบันทึก draft|
|outcome|enum \| null|`success` / `fail` / null (ยังไม่เลือก)|
|evidence|object|โครงสร้างเดียวกับ §6.4 — เก็บเท่าที่กรอกไว้ ไม่ครบก็บันทึกได้|
|travel_origin|object \| null|โครงสร้างเดียวกับ §6.4.1 — เก็บเท่าที่กรอกไว้ ไม่บังคับสำหรับ draft|

Draft ผูกกับ `case_id` 1 ต่อ 1 — เปิดฟอร์มปิดงานเคสเดิมซ้ำจะโหลด draft ล่าสุดอัตโนมัติ ลบ draft ทันทีที่ `submit_close_case` สำเร็จ (ไม่ใช่ draft ที่ค้างอยู่อีกต่อไป)

### 6.6 Expense (ค่าใช้จ่าย)
แยกเป็น 2 กลุ่มตามที่มาของรายการ:

**กลุ่ม "ผูกกับเคส" — ระบบสร้างอัตโนมัติทันทีที่ปิดงาน**
|Field|Type|Description|
|---|---|---|
|case_id|uuid|เคสที่ปิดงานแล้วสร้างรายการนี้|
|type|enum|`fuel` (ค่าน้ำมัน) / `allowance` (เบี้ยเลี้ยง) — คำนวณจาก Compensation Template ของทีม (ไฟล์ 11)|
|amount|decimal|จำนวนเงิน — สำหรับ `type = fuel` โหมด `PER_KM`: คำนวณจาก `travel_origin` + ลำดับ `evidence.checkins` ตามสูตรใน §6.4.2 (ผ่าน Google Maps Distance Matrix API); โหมด `DAILY_FLAT`: ใช้ `daily_flat_rate` คงที่ ไม่ต้องคำนวณระยะทาง — ดู Compensation Template ไฟล์ 11 §7.1|
|distance_km|decimal \| null|เฉพาะ `type = fuel` โหมด `PER_KM` — ระยะทางจริงที่คำนวณได้ (กม.) เก็บไว้เพื่อ audit/ตรวจสอบยอดย้อนหลัง — เป็น null สำหรับ `DAILY_FLAT` หรือ `type = allowance`|
|status|enum|`pending_warehouse_confirm` (เฉพาะเคสสำเร็จ — รอ flag ยืนยันคืนคลังสินค้า) / `pending_approval` (เฉพาะเคสไม่สำเร็จ หรือผ่านขั้นคลังแล้ว — รอ Manager อนุมัติ) / `pending_finance_approval` (ผ่านขั้น Manager แล้ว — รอ Finance อนุมัติ) / `approved` / `rejected` / `needs_revision` (ผู้อนุมัติตีกลับ — รอ field agent แก้ไขเอกสาร) / `superseded` (ถูกแทนที่ด้วยรายการใหม่ — ดู §10.1)|
|date|date|วันที่เกิดรายการ (= วันปิดงาน)|
|reject_reason|string \| null|เหตุผลที่ผู้อนุมัติระบุตอนกด `reject_expense` — บังคับกรอกเมื่อสถานะเปลี่ยนเป็น `needs_revision`|

**กลุ่ม "เบิกแยก" — ผู้ใช้กรอกฟอร์มเบิกเอง**
|Field|Type|Required|Description|
|---|---|---|---|
|date|date|yes|วันที่เข้าพัก — เบิกย้อนหลังได้เสมอ (ไม่บังคับเบิกวันเดียวกับที่พักจริง)|
|amount|decimal|yes|จำนวนเงิน|
|shared_with|uuid \| null|no|พนักงานอีกคนที่พักร่วมห้อง — **เลือกได้จากคนในทีมเดียวกันเท่านั้น** ไม่ระบุไว้ล่วงหน้าว่าต้องเป็นใคร (ใครจ่ายจริงก็เป็นคนเบิก เพราะใบเสร็จมีได้ใบเดียวต่อห้อง)|
|receipt|file|yes|ไฟล์ใบเสร็จแนบ|
|status|enum|—|`pending_approval` / `approved` / `rejected` / `needs_revision` (ผู้อนุมัติตีกลับ — รอ field agent แก้ไขเอกสาร)|
|reject_reason|string \| null|—|เหตุผลที่ผู้อนุมัติระบุตอนกด `reject_expense` — บังคับกรอกเมื่อสถานะเปลี่ยนเป็น `needs_revision`|
|matched_case_ids|array (derived)|—|**Auto-mapping**: ระบบจับคู่อัตโนมัติกับเคสที่มี `schedule_date` ตรงกับ `date` ของรายการเบิกนี้ ไม่ต้องให้ผู้ใช้เลือกเคสเอง — ใช้เพื่อ "ตรวจสอบ" เท่านั้น ไม่มีผลต่อการคำนวณยอดเบิก|

> **กฎสำคัญ — สถานะสำเร็จต้องรอคลังก่อน**: เคสที่ `closed_success` (ได้เครื่องคืน) รายการเบิก fuel/allowance ของเคสนั้นต้องสร้างเป็น `pending_warehouse_confirm` ก่อนเสมอ ห้ามข้ามไป `pending_approval` ตรงจนกว่าจะมี flag ยืนยันว่าเครื่องเข้าคลังจริงแล้ว — flag นี้เชื่อมกับ `HandoverLot.status = confirmed` จากโมดูลคลัง (ไฟล์ 44) ดู Open Items #3 — เคสที่ `closed_fail` ไม่มีขั้นนี้ เข้า `pending_approval` ได้ทันที เพราะไม่มีของต้องตรวจสอบ

> **กฎสำคัญ — ตีกลับเอกสารบัญชี (`reject_expense`)**: ผู้อนุมัติจ่าย (ไฟล์ 16/17 — บัญชี/การเงิน) ที่พบว่าเอกสารเบิกไม่ชัด/ผิด (เช่น ใบเสร็จไม่ชัด, ยอดกรอกผิด) ใช้ปุ่ม `reject_expense` กับ**รายการเบิกนั้นโดยตรง** ไม่ใช่การตีกลับหลักฐานปิดงาน (ดู §10.1 สำหรับกรณีนั้น) — ใช้ได้กับทั้งกลุ่ม "ผูกกับเคส" และ "เบิกแยก" เปลี่ยนสถานะเป็น `needs_revision` พร้อม `reject_reason` บังคับ เฉพาะ field agent เจ้าของรายการแก้ไขและ resubmit ได้ (ผู้จัดการทีมติดตามทรัพย์/หัวหน้าทีมติดตามทรัพย์แก้แทนไม่ได้) — resubmit แล้วกลับเข้า `pending_approval` ตามปกติ (ไม่ผ่านขั้น `pending_warehouse_confirm` ซ้ำ เพราะเป็นแค่การแก้เอกสาร ไม่กระทบสถานะคลัง)

### 6.8 Derived / Computed Fields
- `success_rate` — % ความสำเร็จสะสมตลอดการทำงาน (เคสสำเร็จ ÷ เคสปิดงานทั้งหมด) × 100 — ค่ากลางเดียวกับที่ไฟล์ 40 ใช้แสดงใน agent picker
- `commission_amount` — คอมมิชชั่นที่จะได้รับถ้าเคสสำเร็จ = `Compensation Template.commission` ของทีมพนักงานคนนั้น (ค่าตายตัวต่อเคส ไม่ใช่ % ของมูลหนี้) — แสดงให้เห็น**ก่อนกดรับงาน**เสมอ เพื่อเป็นข้อมูลประกอบการตัดสินใจ
- `no_success_fee_amount` — เบี้ยเสี่ยง/ค่าออกพื้นที่ที่จะได้รับถ้าเคสไม่สำเร็จ = `Compensation Template.no_success_fee` ของทีม

## 7. UI Requirements

### 7.1 Dashboard (หน้าแรก)
แสดงภาพรวมของพนักงานคนนั้นเป็นหลัก ไม่ใช่หน้า "ดูเคส" — มี 5 บล็อกข้อมูล:
1. **แจ้งเตือน Draft ค้าง** (ถ้ามี) — บล็อกสีส้มเด่นบนสุด แตะแล้วไปแท็บ "กำลังติดตาม" ทันที
2. **เคสที่ต้องไปวันนี้** (ถ้ามี `schedule_date` = วันนี้) — การ์ดสีเข้มพร้อมลำดับ แตะแต่ละเคสเปิดรายละเอียดได้
3. **สรุปภาพรวม** — จำนวนเคส 3 สถานะ (รอรับงาน/กำลังติดตาม/สำเร็จ)
4. **% ความสำเร็จสะสม** และ **คอมมิชชั่นเดือนนี้** (กดแล้วไปหน้าสรุปรายได้)
5. **แนวโน้มผลงาน 7 วันล่าสุด** — กราฟแท่งแสดงจำนวนเคสปิดสำเร็จ/ไม่สำเร็จต่อวัน

Desktop: จัดเป็น 2 คอลัมน์ (เนื้อหาหลัก 2/3 + sidebar สรุปด่วน 1/3) แทนการเรียงซ้อนแนวตั้งแบบ mobile

### 7.2 แท็บ "รอรับงาน"
- List เคสสถานะ `pending_accept` ของพนักงานคนนั้น
- แต่ละการ์ด: ชื่อลูกหนี้, ที่อยู่ปัจจุบัน (province/district), ทรัพย์, มูลหนี้, เวลาที่มอบหมาย
- ปุ่ม **"ดูรายละเอียด"** (เปิด modal เต็มแบบ §7.7 — เห็นกล่องคอมมิชชั่นด้วยเพราะยัง `pending_accept`) และปุ่ม **"รับงาน"** (action ตรง ไม่ต้องเปิด modal ก่อนก็ได้)
- กดรับงานจากปุ่มไหนก็ได้ผลเดียวกัน: เปลี่ยนสถานะเป็น `accepted_unscheduled`

### 7.3 แท็บ "รับงานแล้ว" (จัดวันที่)
- **Toggle 2 มุมมอง**: "ของฉัน" (default) / "ทีม"
  - **ของฉัน**: List เคสที่ยังไม่จัดวัน พร้อมปุ่ม "จัดวันที่" ต่อเคส
  - **ทีม**: เห็นเคสที่ยังไม่จัดวันของ**ทุกคนในทีมเดียวกัน** (ตาม `Team.id` จากไฟล์ 40) แยกเป็นคอลัมน์ต่อคน **เห็นรายละเอียดเต็ม** (ชื่อลูกหนี้, จังหวัด) เพราะเป็นทีมเดียวกันไว้ใจได้ — ใช้ดูประกอบการวางแผนว่าใครไปโซนไหน ก่อนจะลงวันของตัวเอง (เผื่อนัดพักที่พักร่วมกันได้)
- กด "จัดวันที่" เปิด modal เลือกวันที่ (§7.5)

### 7.4 Calendar Picker (เลือกวันที่ติดตาม)
- **Custom calendar grid แบบ Google Calendar** — แสดงเดือนปัจจุบัน เลื่อนเดือนก่อน/หลังได้ ไม่ใช้ `<input type="date">` ของเบราว์เซอร์ เพราะต้องโชว์ badge จำนวนเคสต่อวันด้วย
- แต่ละวันที่มีเคสจัดไว้แล้ว (ของพนักงานคนนั้น) แสดง **badge ตัวเลข** มุมขวาบนของวันนั้น
- **คลิกวันที่**: เปิด popup เล็กเสมอ (ไม่ assign ทันทีจากการคลิกเฉยๆ)
  - ถ้าวันนั้นมีเคสอยู่แล้ว → popup แสดงรายการเคสที่มีอยู่ + ปุ่ม "ยืนยันเลือกวันนี้" (จะกลายเป็นลำดับต่อจากเคสที่มีอยู่)
  - ถ้าวันนั้นว่าง → popup แสดงข้อความยืนยันเฉยๆ + ปุ่ม "ยืนยันเลือกวันนี้"
- วันที่ผ่านไปแล้ว (ก่อนวันนี้) กดไม่ได้ (disabled)
- **ใต้ปฏิทินแสดงรายละเอียดเคสแบบเต็ม** (โครงสร้างเดียวกับ §7.7 Case Detail) แบบ static ไม่ต้องกดเปิด modal แยกอีกชั้น — เพื่อให้เห็นข้อมูลประกอบการเลือกวันโดยไม่ต้องสลับหน้าจอ
- ถ้ามีเพื่อนร่วมทีมมีเคสในจังหวัดเดียวกันช่วงที่กำลังจะจัดวัน แสดง **banner สีม่วงเตือน** แนะนำให้คุยเรื่องที่พัก/เส้นทางร่วมกัน (ไม่บล็อกการเลือก เป็นแค่ข้อมูลแนะนำ)

### 7.5 แท็บ "กำลังติดตาม"
- จัดกลุ่มเคสตาม `schedule_date` แสดงเป็น section ต่อวันเรียงจากใกล้ไปไกล
- ในแต่ละวัน เคสเรียงตาม `schedule_order` พร้อมเลขลำดับหน้าการ์ด — **ลากสลับลำดับได้เสมอ ไม่มีกฎ lock** (ลากข้ามเคสไปก่อนได้ทุกเมื่อ เผื่อเหตุฉุกเฉิน)
- **ปุ่มหลักของการ์ดมี 2 สถานะ** แทนปุ่ม "ปิดงาน" เดิม:
  - **"เริ่มงาน"** (ค่าเริ่มต้น — ยังไม่มี `travel_origin`/`evidence.checkins` ของเคสนี้เลย) — กดแล้วเปิดฟอร์มปิดงาน (§7.6) ทันที พร้อม**ดึง GPS อัตโนมัติเป็น `travel_origin`** ให้เลยโดยไม่ต้องกดปุ่มแยกอีกขั้น (ปรับตำแหน่งได้ทีหลังตามปกติ) แล้วให้กดเช็คอินจุดเริ่มต้นต่อได้ทันที
  - **"จบงาน"** (เปลี่ยนจาก "เริ่มงาน" ทันทีหลังกดครั้งแรก ไม่ว่าจะ submit สำเร็จหรือยังไม่ submit ก็ตาม) — กดแล้วเปิดฟอร์มเดิม **ต่อจากที่ทำไว้ก่อนหน้า** (travel_origin/เช็คอิน/รูป/วิดีโอที่กรอกไว้ไม่หาย แม้จะปิด modal ออกไปทำอย่างอื่นก่อนแล้วค่อยกลับมา) เพื่อเลือก outcome และยืนยันปิดงานจริง
  - **เปิด-ปิด modal ระหว่างทางได้ไม่จำกัดจำนวนครั้ง** — กดเริ่มงานแล้วปิด modal ไปดูเคสอื่นก่อนได้ ข้อมูลที่กรอกไว้ (travel_origin, checkins, photos, videos, outcome) เก็บอยู่ใน Close-Case Draft เสมอ (ดู §6.5) จนกว่าจะ `submit_close_case` สำเร็จจริง
  - ปุ่มนี้ไม่เกี่ยวกับทีม `PER_KM`/`DAILY_FLAT` — แสดง "เริ่มงาน"/"จบงาน" เหมือนกันทุกทีม เพราะใช้สำหรับเช็คอินด้วย (ทีม `DAILY_FLAT` ก็ยังต้องเช็คอินตามปกติ แค่ไม่มีการคำนวณระยะทางค่าน้ำมัน)
- การ์ดที่มี Draft ค้าง (กดเริ่มงานไปแล้วแต่ยังไม่ submit) แสดง badge "Draft" สีส้ม ปุ่มเป็น "จบงาน" ตามที่อธิบายข้างต้น
- **การ์ดที่มี `pending_reassignment` ค้างตอบ** แสดง badge "รอตอบคำขอเปลี่ยน" สีม่วง และปุ่มเปลี่ยนเป็น **"ตอบคำขอ"** สีม่วง (แทนปุ่มเริ่มงาน/จบงาน) — ดูรายละเอียดเต็มที่ §7.8

### 7.6 ฟอร์มปิดงาน (Close Case)
- **เมื่อเปิดฟอร์มนี้ครั้งแรกของเคส (กดปุ่ม "เริ่มงาน")**: ระบบดึงพิกัด GPS ปัจจุบันจาก device อัตโนมัติเป็น `travel_origin` ทันทีโดยไม่ต้องกดปุ่มแยก — แสดงเป็นกล่อง "จุดเริ่มเดินทาง" พร้อมแผนที่และปุ่ม "ปรับตำแหน่ง" ให้ลากแก้ไขได้อิสระถ้าตำแหน่งไม่ตรง (กล่องนี้แสดงเฉพาะทีมที่ใช้ Fuel Rule โหมด `PER_KM` เท่านั้น ทีม `DAILY_FLAT` ไม่แสดง เพราะไม่ต้องคำนวณระยะทาง)
- **`travel_origin` คนละชุดข้อมูลกับ `evidence.checkins`** เหมือนเดิม — ไม่ใช่หลักฐาน เป็นแค่จุดอ้างอิงคำนวณเงิน แก้ไขได้เสมอไม่ล็อก (ดู §6.4.1)
- **บังคับต้องมี `travel_origin` ก่อน `submit_close_case` จะสำเร็จ** (เฉพาะทีม `PER_KM`) — แต่เนื่องจากตอนนี้ระบบดึงอัตโนมัติให้ทันทีที่เปิดฟอร์ม กรณีปกติจะมีอยู่แล้วเสมอ ยกเว้นกรณีแปลกที่ระบบดึง GPS ไม่ได้ (เช่น ปิดสิทธิ์ตำแหน่ง) — ถ้าไม่มี ระบบ reject พร้อมข้อความแจ้งหลักฐานที่ขาด เหมือนกับเช็คอิน/รูป/วิดีโอ (ดู §12)
- **เลือก outcome ก่อน**: 2 ปุ่มใหญ่ "สำเร็จ" / "ไม่สำเร็จ" (การ์ดใหญ่ icon เด่น ป้องกันกดผิด)
- หลังเลือก outcome แสดง section หลักฐานแยกชัดเจน:
  - **เช็คอิน** (บังคับอย่างน้อย 1 จุด) — ปุ่มเช็คอินดึงพิกัด GPS ปัจจุบันจริงทันที ไม่ใช่กรอกมือ แต่ละจุดมี static map preview + ปุ่มลบ — กดเพิ่มได้หลายจุด
  - **รูปถ่าย** (บังคับอย่างน้อย 1 รูป) — grid thumbnail เพิ่ม/ลบได้ทีละไฟล์
  - **วิดีโอ** (บังคับอย่างน้อย 1 คลิป) — grid thumbnail เพิ่ม/ลบได้ทีละไฟล์ แยก section จากรูปถ่ายชัดเจน
  - **รูปสินค้ายืนยัน** (บังคับเฉพาะ outcome = สำเร็จ) — section แยก ไม่แสดงเลยถ้าเลือกไม่สำเร็จ
  - **เสียงบันทึกการสนทนา** (ไม่บังคับทุก outcome)
- **ปุ่ม 2 ปุ่มท้ายฟอร์ม**: "บันทึก Draft" (บันทึกเท่าที่กรอกไว้ ปิดฟอร์มกลับไป list) และ "ยืนยันปิดงาน" (ต้องครบหลักฐานบังคับตาม outcome ก่อน — validation ตาม §12)

> **โหมดแก้ไขหลักฐาน (`needs_revision`)** — เมื่อเคสถูก**เจ้าหน้าที่อนุมัติเคส (system role)** ตีกลับ (ดู §10.1) ฟอร์มนี้เปิดขึ้นมาในโหมดแก้ไขโดยอัตโนมัติ พร้อมกล่องแบนเนอร์สีเหลือง/ส้มแสดง `reject_reason` ที่เจ้าหน้าที่อนุมัติเคสระบุไว้ค้างอยู่บนสุดของฟอร์มเสมอ — ข้อจำกัดของโหมดนี้:
> - **เช็คอินทุกจุดล็อกไว้ตามเดิมทั้งหมด** — ไม่มีปุ่มเพิ่ม/ลบ/แก้ไขจุดเช็คอิน เพราะเป็นพิกัด GPS จริงที่เกิดขึ้น ณ เวลานั้น ย้อนไปแก้ไขให้ตรงความจริงไม่ได้
> - **`travel_origin` ปรับตำแหน่งได้ตามปกติ** เหมือนโหมดปกติ (ไม่ใช่หลักฐาน เป็นแค่จุดคำนวณเงิน — ดู §6.4.1) — ถ้าปรับ ระบบคำนวณระยะทาง/ยอดค่าน้ำมันใหม่ตอน `resubmit_close_case`
> - **Outcome (สำเร็จ/ไม่สำเร็จ) ล็อกไว้ตามเดิม** — ไม่มีปุ่มให้สลับ outcome ในโหมดนี้ (ถือว่าเป็นข้อเท็จจริงที่ชัดเจนอยู่แล้วว่าได้เครื่องคืนหรือไม่ ไม่ใช่สิ่งที่ตีกลับเพื่อแก้)
> - **แก้ไขได้เฉพาะ**: รูปถ่าย, วิดีโอ, เสียงบันทึกการสนทนา, รูปสินค้ายืนยัน (เพิ่ม/ลบ/แทนที่ไฟล์ได้ตามปกติ)
> - ปุ่มท้ายฟอร์มเปลี่ยนเป็น "ส่งกลับยืนยันอีกครั้ง" ปุ่มเดียว (ไม่มีปุ่ม "บันทึก Draft" ในโหมดนี้ เพราะเคสนี้ไม่ใช่งานที่ยังไม่เคยปิด)

### 7.7 Case Detail (รายละเอียดเคสแบบเต็ม)
ใช้ component เดียวกันใน 3 ที่: modal ดูรายละเอียด, ใต้ปฏิทินเลือกวันที่ (§7.4), และในกล่องคำขอเปลี่ยนผู้รับผิดชอบ (§7.8) — เนื้อหาประกอบด้วย:
- สรุปเคส (ลูกหนี้, case_ref, ไฟแนนซ์, ทรัพย์, **tracking_round ปัจจุบัน**)
- **กล่องคำขอเปลี่ยนผู้รับผิดชอบ** (ถ้ามี `pending_reassignment`) — แสดงเด่นด้วยกรอบสีม่วง พร้อมปุ่ม "ตอบคำขอนี้"
- **กล่องคอมมิชชั่น** (ถ้าสถานะยัง `pending_accept`) — แสดงยอดคอมมิชชั่นถ้าสำเร็จ ไม่รวมค่าน้ำมัน/เบี้ยเลี้ยง/ที่พัก
- เลขบัตรประชาชน, มูลหนี้คงเหลือ, ทรัพย์ (พร้อม IMEI)
- **3 ที่อยู่** (ปัจจุบัน/ที่ทำงาน/ตามบัตร) แต่ละที่อยู่มีปุ่มเปิด Google Maps แยกอิสระ
- **ช่องทางติดต่อ** — กดโทร/LINE/Facebook เปิดแอป/ลิงก์จริงได้ทันที
- ผู้ติดต่ออื่น (ถ้ามี) — กดโทรได้เหมือนกัน
- เอกสารแนบ — กดเปิดดูได้จริง (ไม่ใช่แค่ badge บอกมี/ไม่มี)
- รูปสินค้า — grid กดดูภาพขยายได้
- ปุ่ม "รับงาน" (เฉพาะตอน `pending_accept`)

### 7.8 Pending Reassignment Flow (ตอบรับ/ปฏิเสธคำขอเปลี่ยนผู้รับผิดชอบ)
- **Auto-popup**: เปิดแอป/โหลดหน้าใหม่ตอนใดก็ตามที่มี `pending_reassignment` ที่ยังไม่ตอบและยังไม่ถูกกด "ดูทีหลัง" ในเซสชันนี้ — popup เด้งขึ้นมาทันที แสดงสรุปคำขอ + เวลาหมดเขต
- **ไม่บล็อกแบบเข้ม** — มีปุ่ม "ดูทีหลัง" ให้ปิด popup ได้ แต่หลังปิดแล้ว **badge สีม่วงยังค้างอยู่ที่เมนู "กำลังติดตาม"** (ทั้ง bottom nav/sidebar และที่การ์ดเคสนั้น) จนกว่าจะตอบจริง — กันไม่ให้คำขอเงียบหายจากสายตาพนักงานที่อาจกำลังขับรถ/ทำงานเร่งอยู่
- **ปุ่ม "ยินยอม"**: เปลี่ยนผู้รับผิดชอบทันที (ของจริงคือเปลี่ยน `agent_id` ในไฟล์ 40 + ล้าง `accepted_at` ให้คนใหม่กดรับงานใหม่) เคสหายจากรายการของพนักงานคนเดิม
- **ปุ่ม "ไม่ยินยอม"**: ต้องกรอกเหตุผลก่อนยืนยันเสมอ (`decline_reason` ตามไฟล์ 40 §8) — เคสยังเป็นของพนักงานคนเดิมตามปกติ ไม่มีอะไรเปลี่ยน
- เข้าถึง flow นี้ได้ 3 ทาง: auto-popup, ปุ่ม "ตอบคำขอ" ที่การ์ดเคสในแท็บกำลังติดตาม, หรือปุ่ม "ตอบคำขอนี้" ในหน้ารายละเอียดเคส — ทั้ง 3 ทางเปิด modal เดียวกัน

> **เคสถูก auto-resolve ไปแล้ว (พนักงานไม่ได้ตอบทันเวลา)** — ต่างจาก flow ข้างต้นที่ยังรอคำตอบ กรณีนี้**จบไปแล้ว แก้ไขอะไรไม่ได้** จึง**ไม่ใช้ auto-popup แบบบล็อก**เหมือนคำขอที่ยังรอตอบ — แทนที่ด้วย **toast เบาๆ auto-dismiss เอง** (หายไปเองภายในไม่กี่วินาที ไม่ต้องกดปิด) เด้งครั้งเดียวตอนเปิดแอปครั้งแรกหลังเกิดเหตุ ข้อความสั้นๆ เช่น "เคส [ชื่อลูกหนี้] ถูกโอนไปแล้วเพราะไม่ได้ตอบทันเวลา" — รายละเอียดเต็ม (เวลาที่โอน, ชื่อพนักงานคนใหม่) ดูย้อนหลังได้ที่การ์ดในแท็บ "จบงาน" (สถานะ `reassigned_away` ดู §7.11)

### 7.9 เบิกค่าใช้จ่าย
- **2 แท็บ**: "ผูกกับเคส" (default) / "เบิกแยก"
- **แท็บผูกกับเคส**: จัดกลุ่มตามเคส — 1 เคส = 1 แถวสรุป (รวมยอด fuel+allowance) กดขยายดูรายละเอียดแต่ละประเภทได้ — filter ตามสถานะ (รอยืนยันคืนคลัง/รออนุมัติจ่าย/อนุมัติแล้ว)
- **แท็บเบิกแยก**: รายการที่พักที่กรอกฟอร์มเอง — filter ตามสถานะ + เดือน (เพราะสะสมข้ามเวลาได้ ต่างจากรายการผูกเคสที่กรองแค่สถานะพอ) มีปุ่ม "เบิกที่พัก" เปิดฟอร์มกรอกใหม่ (วันที่, จำนวนเงิน, พักร่วมกับใคร [เลือกจากทีมเท่านั้น], แนบใบเสร็จ)
- สรุปยอด "รอดำเนินการ" / "อนุมัติแล้ว" รวมทั้ง 2 กลุ่มแสดงด้านบนเสมอ

### 7.10 สรุปรายได้
- Default แสดง**สะสมตลอด** (ไม่กรองเดือน) มี dropdown กรองเฉพาะเดือนได้
- กล่องใหญ่แสดงยอดคอมมิชชั่นรวม + จำนวนเคสสำเร็จ
- แยกสถิติ "เคสสำเร็จ" (พร้อมยอดคอมมิชชั่น) กับ "เคสไม่สำเร็จ" (พร้อมยอดเบี้ยเสี่ยง) เป็น 2 กล่อง
- รายการเคสที่ปิดแล้วทั้งหมดในช่วงที่กรอง พร้อม badge สถานะและยอดที่ได้ต่อเคส

### 7.11 แท็บ "จบงาน"
- Filter 2 แบบทำงานร่วมกัน: **pill สถานะ** (ทั้งหมด/สำเร็จ/ไม่สำเร็จ/**ถูกโอนไป**) + **dropdown เดือน**
- แต่ละการ์ดแสดงสถานะ, วันที่ปิดงาน, รอบที่ติดตาม, และสถานะค่าใช้จ่ายที่เกี่ยวข้อง
- **การ์ดสถานะ `reassigned_away`** แสดงข้อมูลต่างจากการ์ดปิดงานปกติ — ไม่มีสถานะค่าใช้จ่าย (ไม่มีรายการเบิกเงินเกิดขึ้น เพราะไม่ใช่ผลการปิดงาน) แสดงแทนด้วย: เวลาที่ถูกโอน, เหตุผล (`เกินกำหนดเวลาตอบรับ` หรือเหตุผลที่ผู้จัดการระบุถ้ายินยอมเอง), ชื่อพนักงานคนใหม่ที่รับเคสต่อ

|reject_evidence|ตีกลับหลักฐาน (สงสัยหลักฐานปิดงานไม่น่าเชื่อถือ)|เปลี่ยน `assignment_status` จาก `closed_success`/`closed_fail` → `needs_revision` พร้อมบังคับกรอกเหตุผล — ไม่เพิ่ม `tracking_round`|**เจ้าหน้าที่อนุมัติเคส (system role — เดียวกับที่อนุมัติ recycle ในไฟล์ 38) เท่านั้น** — คนละ role กับ "ผู้จัดการทีมติดตามทรัพย์ (Manager)" หรือหัวหน้าทีมติดตามทรัพย์ที่กด `reassign_case` ในไฟล์นี้ แม้ชื่อจะคล้ายกัน (ดูไฟล์ 38 §5 และไฟล์ 40 §5 สำหรับความแตกต่างของ role)|
|resubmit_close_case|ส่งกลับยืนยันอีกครั้ง (ในโหมด `needs_revision`)|ตรวจว่ามีการแก้ไขรูป/วิดีโอ/เสียง/รูปสินค้าอย่างน้อย 1 รายการ → เปลี่ยนสถานะกลับเป็น `closed_success`/`closed_fail` เดิม (ห้ามเปลี่ยน outcome/เช็คอิน) → mark รายการเบิก fuel/allowance เดิมของรอบนี้เป็น `superseded` → สร้างรายการเบิกใหม่ตามกฎปกติ (§6.6)|Field Agent (เฉพาะเคสตนเอง)|
|reject_expense|ตีกลับรายการเบิก (เอกสารบัญชี/ใบเสร็จผิดหรือไม่ชัด)|เปลี่ยน `expense.status` จาก `pending_approval` หรือ `pending_finance_approval` → `needs_revision` พร้อมบังคับกรอก `reject_reason` (ตีกลับได้จากทุกขั้นอนุมัติ — ตรงกับ `23-finance-state-machines.md` §6.3) — ใช้ได้กับทั้งกลุ่ม "ผูกกับเคส" และ "เบิกแยก" — ไม่กระทบ `assignment_status` ของเคส|ผู้อนุมัติจ่าย (บัญชี/การเงิน ตามไฟล์ 16/17)|
|resubmit_expense|แก้ไขแล้วส่งใหม่ (รายการเบิกที่ถูกตีกลับ)|แก้ไขข้อมูล/ไฟล์แนบของรายการเบิกนั้น → เปลี่ยนสถานะกลับเป็น `pending_approval`|Field Agent (เฉพาะเจ้าของรายการเบิกนั้น — เจ้าหน้าที่อนุมัติเคสหรือผู้จัดการทีมติดตามทรัพย์/หัวหน้าทีมติดตามทรัพย์แก้แทนไม่ได้)|
|respond_reassignment_consent|ยินยอม / ไม่ยินยอม|ตามไฟล์ 40 §8 — ยินยอม: โอนเคสไปคนใหม่ทันที. ไม่ยินยอม (ต้องมี `decline_reason`): ยกเลิกคำขอ ไม่มีอะไรเปลี่ยน|Field Agent (เฉพาะเคสที่ตนถือและถูกขอเปลี่ยน)|
|dismiss_reassignment_popup|ดูทีหลัง|ปิด auto-popup ชั่วคราว ไม่ตอบคำขอ — badge เตือนยังคงอยู่จนกว่าจะตอบจริง|Field Agent|
|submit_hotel_claim|ส่งคำขอเบิก (ที่พัก)|สร้างรายการเบิกแยกสถานะ `pending_approval` พร้อม auto-mapping กับเคสที่ตรงวันที่|Field Agent|

## 9. Workflow
```
[ไฟล์ 40: assigned] → pending_accept → (accept_case) → accepted_unscheduled
                                                              ↓ (schedule_case)
                                                          scheduled (จัดลำดับ/สลับได้เสมอ)
                                                              ↓ (submit_close_case)
                                              closed_success ←┴→ closed_fail
                                                  ↓                  ↓
                                      [ไฟล์ 43: ผลสำเร็จ]   [ไฟล์ 38 §6.6: เปิดโอกาส
                                                              create_recycle_request]

[จาก closed_success หรือ closed_fail — เจ้าหน้าที่อนุมัติเคส (system role) สงสัยหลักฐานปิดงาน]
  → กด reject_evidence + เหตุผล → needs_revision
       → field agent แก้ไขรูป/วิดีโอ/เสียง/รูปสินค้า (เช็คอิน+outcome ล็อกตามเดิม)
       → resubmit_close_case → กลับ closed_success/closed_fail เดิม
            → รายการเบิกรอบเดิม mark เป็น superseded, สร้างรายการเบิกใหม่ (§6.6)

[ระหว่าง accepted_unscheduled หรือ scheduled — ไม่ว่าขั้นไหน]
  → ผู้จัดการกด reassign_case (เคส accepted แล้ว) → pending_reassignment ปรากฏที่นี่
       ├─ พนักงานกด "ยินยอม" → เคสโอนไปคนใหม่ (หายจากรายการพนักงานคนนี้)
       ├─ พนักงานกด "ไม่ยินยอม" + เหตุผล → ยกเลิกคำขอ เคสยังอยู่กับพนักงานคนนี้
       └─ ไม่ตอบจนหมดเขต → ระบบ auto-resolve โอนไปคนใหม่ (ตามไฟล์ 40)
```
- การปิดงานเป็น terminal action ของไฟล์นี้ — เคสที่ `closed_success`/`closed_fail` ไม่กลับมาอยู่ในรายการงานของพนักงานคนนั้นอีก (ย้ายไปแท็บ "จบงาน" เป็น read-only)
- เคสที่ `closed_fail` แล้วถูกอนุมัติ recycle จากไฟล์ 38 จะกลับมาเป็นเคสใหม่ใน pipeline (ผ่านไฟล์ 40 มอบหมายใหม่) — เสมือนเป็นเคสใหม่ในไฟล์นี้ แม้จะใช้ `case_id` เดิม แต่ `tracking_round` เพิ่มขึ้น

## 10. Status / State Machine
|State|Meaning|Allowed Next States|Trigger|
|---|---|---|---|
|pending_accept|มอบหมายแล้ว รอพนักงานกดรับ|accepted_unscheduled|accept_case|
|accepted_unscheduled|รับงานแล้ว ยังไม่จัดวันที่|scheduled / reassigned_away|schedule_case / resolve_reassignment_timeout|
|scheduled|จัดวันที่แล้ว กำลังดำเนินงาน|closed_success / closed_fail / reassigned_away|submit_close_case / resolve_reassignment_timeout|
|closed_success|ปิดงานสำเร็จ (terminal ในไฟล์นี้ ยกเว้นถูกตีกลับ — ส่งต่อไฟล์ 43 เพื่อบันทึกผล)|needs_revision|reject_evidence (เจ้าหน้าที่อนุมัติเคส system role เท่านั้น)|
|closed_fail|ปิดงานไม่สำเร็จ (terminal ในไฟล์นี้ ยกเว้นถูกตีกลับ แต่เปิดโอกาส recycle จากไฟล์ 38)|needs_revision / — (เปิดใหม่ผ่าน `case.recycle_approved` ของไฟล์ 38 → กลับมาเป็น `pending_accept` รอบใหม่)|reject_evidence (เจ้าหน้าที่อนุมัติเคส system role เท่านั้น) / create_recycle_request → approve_recycle (ไฟล์ 38)|
|needs_revision|ถูกเจ้าหน้าที่อนุมัติเคส (system role) ตีกลับหลักฐานปิดงาน รอ field agent แก้ไข|closed_success / closed_fail (เดิม — ตาม outcome ที่ submit ครั้งแรก)|resubmit_close_case|
|reassigned_away|เคสถูกโอนไปพนักงานคนใหม่แล้ว — terminal **สำหรับพนักงานคนเดิม** เท่านั้น (ไม่นับเข้า `success_rate` เพราะไม่ใช่ผลการปิดงาน) — เคสยังดำเนินต่อตามปกติในมุมมองของพนักงานคนใหม่ (เป็นเคสใหม่ใน `pending_accept` ของเขา ไม่ใช่ state เดียวกัน)|—|—|

> หมายเหตุ: state เหล่านี้คือ `assignment_status` ของไฟล์นี้ ซึ่งเป็น sub-state ต่อจาก `case.status = approved` ของไฟล์ 38 — ไม่ใช่ state machine เดียวกัน การวนกลับจาก `closed_fail` ไป `pending_accept` ใหม่ ไม่ใช่ "ย้อนสถานะ" แต่เป็นรอบใหม่ทั้งหมด (`tracking_round` เปลี่ยน, assignment record เป็นอันใหม่ตามไฟล์ 40) — ในขณะที่การวนผ่าน `needs_revision` กลับไป `closed_success`/`closed_fail` เดิม **ไม่เพิ่ม** `tracking_round` เพราะเป็นการแก้ไขหลักฐานของรอบเดิม ไม่ใช่รอบใหม่
> `reassigned_away` เกิดได้จาก 2 ทาง — (1) ผู้จัดการทีมติดตามทรัพย์/หัวหน้าทีมติดตามทรัพย์กด `reassign_case` แล้วพนักงานคนเดิมกด "ยินยอม" ทันที หรือ (2) ไม่ตอบจนครบ `expires_at` ระบบ `resolve_reassignment_timeout` อัตโนมัติ (ตามไฟล์ 40 §8) — ทั้งสองทางจบลงที่ `reassigned_away` เหมือนกันในมุมมองไฟล์นี้ ต่างกันแค่ `reassignment_history.resolution` (`consented` / `timeout_auto`) ที่เก็บไว้ในไฟล์ 40

### 10.1 QC Outcome — สรุปกฎการตีกลับ (ปิด Open Item #9)

ระบบไม่มีขั้น QC แยกก่อนปิดงานเป็นทางการ — ขั้นอนุมัติจ่ายเงิน (ไฟล์ 16/17) ทำหน้าที่ตรวจสอบในตัวอยู่แล้ว เนื่องจากทุกเคสที่ปิดงาน (สำเร็จ/ไม่สำเร็จ) ต้องสร้างรายการเบิกเงินเสมอ และต้องผ่านอนุมัติจ่ายทุกครั้ง แต่มี 2 เส้นทาง "ตีกลับ" แยกตามประเภทปัญหา ห้ามใช้สลับกัน:

|ประเภทปัญหา|ผู้สั่งตีกลับ|Action|กระทบ|ใครแก้ไขได้|ผลหลัง resubmit|
|---|---|---|---|---|---|
|เอกสารบัญชี/ใบเสร็จผิดหรือไม่ชัด|ผู้อนุมัติจ่าย (บัญชี/การเงิน ไฟล์ 16/17)|`reject_expense`|เฉพาะ `expense.status` ของรายการเบิกนั้น → `needs_revision`|Field Agent เจ้าของรายการเท่านั้น|กลับเข้า `pending_approval` — `assignment_status` ไม่กระทบเลย|
|หลักฐานปิดงานน่าสงสัย (ไม่น่าเชื่อถือ/ไม่ตรงพื้นที่)|**เจ้าหน้าที่อนุมัติเคส (system role เดียวกับที่อนุมัติ recycle ในไฟล์ 38) เท่านั้น** — ไม่ใช่ผู้จัดการทีมติดตามทรัพย์/หัวหน้าทีมติดตามทรัพย์ของไฟล์ 40/41|`reject_evidence`|`assignment_status` ทั้งเคส → `needs_revision`|Field Agent เจ้าของเคส — แก้ได้เฉพาะรูป/วิดีโอ/เสียง/รูปสินค้า (เช็คอิน+outcome ล็อกตามเดิม)|กลับเป็น `closed_success`/`closed_fail` เดิม → รายการเบิกรอบเดิม mark เป็น `superseded`, สร้างรายการเบิกใหม่ตามกฎปกติ (§6.6)|

**ขอบเขตที่ตั้งใจไม่รองรับ (out of scope รอบนี้)**: กรณี field agent เลือก outcome ผิดจริง ๆ (เช่น กดปุ่ม "สำเร็จ" ทั้งที่ไม่ได้เครื่องคืน) ไม่มี flow แก้ไขในระบบ เพราะ outcome ผูกกับข้อเท็จจริงที่ชัดเจน (ได้เครื่องคืนหรือไม่) ซึ่งไม่ควรผิดพลาดได้ง่ายเท่าหลักฐานไม่ชัด — ผู้จัดการต้องจัดการนอกระบบ (ติดต่อพนักงานโดยตรง) ถ้าเกิดกรณีนี้ขึ้นจริง

## 11. Business Rules
- **Mobile และ Desktop ใช้ logic เดียวกัน 100%** — ไม่ตัดฟีเจอร์ฮาร์ดแวร์ (กล้อง/GPS) ออกบน Desktop แม้ความแม่นยำ/พฤติกรรมจะต่างกันตามที่เบราว์เซอร์/อุปกรณ์รองรับ (เช่น คอมไม่มีกล้องอาจเปิด file picker แทนกล้องสด, GPS ของคอมอาจแม่นน้อยกว่ามือถือ) — เป็นความเสี่ยงที่ผู้ใช้ยอมรับแล้วเพื่อความสม่ำเสมอของฟีเจอร์ระหว่าง 2 เวอร์ชัน
- **เช็คอินต้องเป็นพิกัด GPS จริงของอุปกรณ์เท่านั้น** ห้ามมีช่องกรอกพิกัดมือในระบบจริงเด็ดขาด (mockup ปัจจุบัน random พิกัดเพื่อ demo เท่านั้น ของจริงต้องดึงจาก Geolocation API ของอุปกรณ์)
- **หลักฐานบังคับต่างกันตาม outcome**: สำเร็จต้องมีรูปสินค้ายืนยันเพิ่มจากหลักฐานพื้นฐาน (เช็คอิน+รูป+วิดีโอ) ไม่สำเร็จไม่ต้องมีรูปสินค้า — เสียงไม่บังคับทั้งสอง outcome
- **ลำดับงานในแต่ละวันยืดหยุ่นเสมอ** ไม่มีกฎ "ต้องทำตามลำดับ" บังคับ — พนักงานสลับลำดับได้ทุกเมื่อแม้จะข้ามเคสไปก่อนแล้วก็ตาม (เผื่อเหตุฉุกเฉิน)
- **Draft ไม่มี deadline** — บันทึกค้างได้นานเท่าที่ต้องการ จนกว่าจะ submit จริงหรือลบเอง (ไม่มี auto-expire ของ draft ในเฟสนี้)
- **มุมมองทีมเป็น read-only เสมอ** — พนักงานดูเคสของเพื่อนร่วมทีมได้แค่ใน "มุมมองทีม" ของหน้าจัดวันที่เท่านั้น ไม่สามารถแก้ไข/จัดวันที่ให้เพื่อนร่วมทีมจากที่นี่ได้
- **ค่าใช้จ่ายผูกเคสไม่ต้องทำเรื่องเบิกเอง** — ระบบสร้างให้อัตโนมัติทันทีที่ `submit_close_case` สำเร็จ ไม่มีปุ่ม "ยืนยัน/ยอมรับ" จากฝั่งพนักงาน — การจ่ายจริงรวมยอดและจ่ายเป็นรอบ (ไม่ใช่จ่ายทันทีทีละเคส)
- **ที่พักเบิกแยกเสมอ ไม่ผูกกับเคสเดียว** เพราะใบเสร็จ 1 ใบอาจครอบคลุมหลายวัน/หลายเคส — auto-mapping กับเคสเป็นแค่ข้อมูลอ้างอิงสำหรับตรวจสอบ ไม่ใช่ตัวกำหนดยอดเงิน
- **ผู้พักร่วมเลือกได้แค่คนในทีมเดียวกัน** ไม่ระบุไว้ล่วงหน้าว่าต้องเป็นใคร เพราะใบเสร็จมีได้ใบเดียวต่อห้อง ใครจ่ายจริงก็เป็นผู้เบิก

|Scenario|Validation / Error|System Behavior|
|---|---|---|
|กดปิดงานโดยยังไม่เลือก outcome|`CLOSE_OUTCOME_REQUIRED`|reject — ต้องเลือกสำเร็จ/ไม่สำเร็จก่อนเสมอ|

## 14. Audit Log
ทุก mutation บันทึก `actor_id`, `role`, `action`, `before`, `after`, `reason` (เมื่อมี) ตามกฎกลาง รวมถึง:
- การเปลี่ยนสถานะทุกครั้ง (pending_accept→accepted_unscheduled→scheduled→closed_success/closed_fail)
- การจัดวันที่และการสลับลำดับ (`schedule_case`, `reorder_schedule`)
- การบันทึก/ลบ Draft ปิดงาน
- การตอบรับ/ปฏิเสธคำขอเปลี่ยนผู้รับผิดชอบ พร้อม `decline_reason` เมื่อปฏิเสธ (อ้างอิง `reassignment_history` ของไฟล์ 40)
- การสร้างรายการเบิกค่าใช้จ่ายทุกประเภท (อัตโนมัติและเบิกแยก)

## 15. Notifications
- **Platform**: ใช้ **Web Push API** (ไม่ใช่ FCM) — ไม่ต้องมี native app, ทำงานผ่านเบราว์เซอร์/PWA โดยตรง
  - **Android/Chrome/Desktop**: ใช้ได้เต็มรูปแบบโดยไม่มีเงื่อนไขเพิ่มเติม
  - **iOS Safari**: ใช้ได้เฉพาะกรณีพนักงาน "เพิ่มลงหน้าจอโฮม" (Add to Home Screen) ก่อนเท่านั้น — เปิดผ่านแท็บ Safari ธรรมดาจะไม่ได้รับ push เลย — **ไม่บังคับขั้นตอนนี้** แค่แนะนำตอน onboarding ครั้งแรก (เช่น แบนเนอร์ "เพิ่มแอปนี้ลงหน้าจอโฮมเพื่อรับการแจ้งเตือนทันที") พนักงานที่ไม่ทำตามยังใช้แอปได้ตามปกติ แค่ไม่ได้รับ push
  - Subscription ของ Web Push บางครั้งอาจหลุดเองได้ (โดยเฉพาะ iOS) โดยพนักงานไม่รู้ตัว — ไม่ต้องมีกลไกแจ้งเตือนเรื่องนี้แยก เพราะมี fallback หลักรองรับอยู่แล้ว (ดูข้อถัดไป)
- **Fallback หลัก (ใช้เสมอไม่ว่าจะได้ push หรือไม่)**: **In-app notification** ผ่าน badge + list ภายในแอป — พนักงานเห็นรายการที่ต้องตอบ/ต้องรู้เสมอตอนเปิดแอป โดยไม่ต้องพึ่ง push เป็นช่องทางเดียว (เช่น badge สีม่วงที่เมนู "กำลังติดตาม" ตาม §7.8, toast ตอนเปิดแอปตาม §7.8) — ไม่เพิ่ม channel สำรองอื่น (SMS/LINE Notify) ในเฟสนี้
- แจ้งพนักงานทันทีที่มีเคสใหม่เข้าสถานะ `pending_accept` (มอบหมายจากไฟล์ 40)
- แจ้งพนักงานทันทีที่มี `pending_reassignment` ใหม่เข้ามา (auto-popup ในแอป + push notification ถ้ามี)
- แจ้งพนักงานด้วย toast เบาๆ (auto-dismiss) เมื่อเคสของตนถูก auto-resolve เป็น `reassigned_away` (ดู §7.8)
- แจ้งผู้จัดการที่เกี่ยวข้องเมื่อพนักงานตอบรับ/ปฏิเสธคำขอเปลี่ยนผู้รับผิดชอบ
- แจ้งฝ่ายบัญชี/การเงินเมื่อมีรายการเบิกใหม่เข้าสถานะ `pending_approval`

## 16. Integration Points
- event `case.assigned` (รับจากไฟล์ 40) → สร้างเคสในแท็บ "รอรับงาน"
- event `assignment.reassignment_requested` (รับจากไฟล์ 40) → แสดง auto-popup คำขอเปลี่ยนผู้รับผิดชอบ
- event `case.closed_success` / `case.closed_fail` → ส่งต่อไฟล์ 43 (ผลการติดตาม) และไฟล์ 38 (เปิดโอกาส recycle ถ้า fail)
- event `expense.case_bound_created` → สร้างรายการเบิก fuel/allowance อัตโนมัติ ส่งเข้า queue รอคลัง/รออนุมัติของฝ่ายบัญชี
- event `expense.hotel_claim_submitted` → ส่งเข้า queue รออนุมัติของฝ่ายบัญชี

## 19. Acceptance Criteria

## 21. การตัดสินใจที่เกี่ยวข้อง (Decisions)

- **Mobile และ Desktop ใช้ logic เดียวกัน 100%** — ไม่ตัดฟีเจอร์ฮาร์ดแวร์ (กล้อง/GPS) ออกบน Desktop แม้ความแม่นยำจะต่างกันตามอุปกรณ์ (§11)
- **เช็คอินต้องเป็นพิกัด GPS จริงของอุปกรณ์เท่านั้น** ห้ามมีช่องกรอกพิกัดมือในระบบจริงเด็ดขาด (§11)
- **หลักฐานบังคับต่างกันตาม outcome** — สำเร็จต้องมีรูปสินค้ายืนยันเพิ่ม, ไม่สำเร็จไม่ต้องมี — เสียงไม่บังคับทั้งสอง outcome (§11, §6.4)
- **ลำดับงานในแต่ละวันยืดหยุ่นเสมอ ไม่มีกฎต้องทำตามลำดับ** และ **Draft ไม่มี deadline** (§11)
- **มุมมองทีมเป็น read-only เสมอ** พนักงานแก้ไข/จัดวันที่ให้เพื่อนร่วมทีมไม่ได้ (§11)
- **ค่าใช้จ่ายผูกเคสสร้างอัตโนมัติทันทีที่ `submit_close_case` สำเร็จ ไม่ต้องเบิกเอง** — จ่ายจริงรวมยอดเป็นรอบ ไม่จ่ายทันทีทีละเคส (§11)
- **ที่พักเบิกแยกเสมอ ไม่ผูกกับเคสเดียว** เพราะใบเสร็จ 1 ใบอาจครอบคลุมหลายวัน/หลายเคส (§11)
- **ค่าน้ำมันโหมด PER_KM ใช้ Google Maps Distance Matrix API เป็นหลักในเฟสแรก** ไม่ใช่ Pinpoint — ยอดจ่าย = `MIN(ระยะทางจริง × rate_per_km, max_per_case)` ถ้าตั้งเพดานไว้ (§6.4.2, ปิด Open Item เดิม)
- **Push Notification ใช้ Web Push API (ไม่ใช่ FCM)** — fallback หลักคือ in-app notification เสมอไม่ว่าจะได้ push หรือไม่ (§15, ปิด Open Item เดิม)
- **ไม่มีขั้น QC แยกก่อนปิดงานเป็นทางการ** — เพิ่ม flow ตีกลับ 2 เส้นทางแยกตามประเภทปัญหาแทน: `reject_expense` และ `reject_evidence` (§10.1, ปิด Open Item เดิม)
- **Auto-resolve timeout ของ `pending_reassignment` ใช้ toast เบาๆ auto-dismiss** ไม่ใช้ popup บล็อก — เพิ่ม state `reassigned_away` ที่ไม่นับเข้า success_rate (§7.8, §7.11, ปิด Open Item เดิม)
- **ไฟล์ 42 และ 43 (baseline เดิม) merge เข้าไฟล์นี้สมบูรณ์แล้วทั้งหมด** — ดู stub `42-merged-into-41.md`/`43-partially-merged-into-41.md` สำหรับรายละเอียดเหตุผลการ merge

## 22. สิ่งที่ยังต้องตัดสินใจ (Open Items)

1. **Map/จัดเส้นทางอัตโนมัติด้วย GPS routing** — ตัดออกจากเฟสแรกทั้งหมดตามที่ตกลง อาจกลับมาพิจารณาในเฟสถัดไปถ้าจำนวนเคสต่อพนักงานต่อวันเพิ่มขึ้นจนจัดเส้นทางมือไม่ไหว
2. **Offline Support** — ตัดออกจากเฟสแรก ต้องมีอินเทอร์เน็ตเสมอ ถ้าไม่มีเน็ตระบบแจ้งเตือนให้เชื่อมต่อใหม่แทนการทำงานต่อแบบ offline-first — ถ้าจะทำในอนาคตต้องออกแบบ Service Worker + IndexedDB + Sync Queue + Conflict Resolution ใหม่ทั้งหมด เป็นงานใหญ่ที่กระทบสถาปัตยกรรม frontend ทั้งระบบ
3. **โมดูลคลังสินค้า** — ✅ **ปิดแล้ว** — ออกแบบและสร้าง Mockup เสร็จสมบูรณ์แล้ว (ดูไฟล์ 44 — Asset Custody & Handover และ warehouse.html) Flag `pending_warehouse_confirm` ถูกเชื่อมกับ `HandoverLot.status = confirmed` จาก module คลังจริงแล้ว
4. **เอกสารสัญญา/อัปโหลดไฟล์ใหญ่จากคอม** — เป็น use case ที่ระบุไว้ว่าต้องมีบน Desktop (พนักงานพิมพ์สัญญาก่อนออกสนามเพราะระบบจ่ายงานออนไลน์ไม่มีเอกสารตัวจริง, อัปโหลดวิดีโอไฟล์ใหญ่สะดวกกว่าจากคอม) — **ยังไม่ได้ออกแบบ/implement ในรอบนี้** เพราะตัดสินใจให้ Desktop ใช้ logic เดียวกับ Mobile ทั้งหมดแทน (ดู §11) ไม่ได้แยกเป็นหน้าจอเอกสารต่างหากตามที่เคยคิดไว้ตอนแรก — ถ้าจะทำจริงต้องเปิดเป็นโมดูลใหม่แยก ไม่ใช่ส่วนหนึ่งของไฟล์นี้
5. **Pinpoint Geocoding API** — มีผลทดสอบ API เบื้องต้นแล้ว (เก็บไว้ในเอกสารทดสอบแยก) ทราบว่า Autocomplete ไม่มี grade/confidence score คืนทั้งที่อยู่และ POI ปนกัน ต้องมีคนเลือกผลลัพธ์เอง — ยังไม่ได้ implement การเรียก API จริงในไฟล์นี้ เพราะที่อยู่ทั้ง 3 ชุดที่ใช้ในปัจจุบันรับ `lat`/`lng` มาจากไฟล์ 38 อยู่แล้ว (กรอกตอนสร้างเคส) ไม่ต้อง geocode ซ้ำในไฟล์นี้ — **อัปเดต**: ค่าน้ำมันโหมด PER_KM ตัดสินใจใช้ Google Maps Distance Matrix API เป็นหลักในเฟสแรกแล้ว (ดู §6.4.2) ไม่ใช้ Pinpoint สำหรับเรื่องนี้ — Pinpoint ยังเก็บไว้พิจารณาเป็นตัวเลือก default ในอนาคต (เฟสถัดไป) เผื่อย้ายมาใช้ Pinpoint Route ทดแทน Google Maps ทีหลัง
6. ~~**ค่าน้ำมันโหมด PER_KM — แหล่งระยะทางจริง**~~ — **ปิดแล้ว** (สัมภาษณ์และออกแบบเสร็จสมบูรณ์ — ดู §6.4.1, §6.4.2, §6.6, §7.6, §8) สรุปสั้น: เพิ่มปุ่ม "เริ่มเดินทาง" (`set_travel_origin`) ก่อนฟอร์มปิดงานของทุกเคส ดึง GPS จริงเป็นค่าเริ่มต้นแล้วปรับตำแหน่งได้อิสระ (คนละชุดข้อมูลกับ `evidence.checkins` ที่ล็อกตลอด) — ระยะทางคำนวณสะสมตามลำดับ `travel_origin → checkins[1..n]` ผ่าน **Google Maps Distance Matrix API** (เฟสแรก) — ยอดจ่าย = `MIN(ระยะทางจริง × rate_per_km, max_per_case)` ถ้าตั้งเพดานไว้ ไม่มีเพดานถ้าไม่ตั้งค่า
7. ~~**Auto-resolve timeout ของ pending_reassignment**~~ — **ปิดแล้ว** (สัมภาษณ์และออกแบบเสร็จสมบูรณ์ — ดู §7.8, §7.11, §10) สรุปสั้น: ไม่ใช้ auto-popup บล็อกเหมือนคำขอที่ยังรอตอบ เพราะกรณีนี้จบไปแล้วแก้ไขอะไรไม่ได้ — ใช้ toast เบาๆ auto-dismiss เด้งครั้งเดียวตอนเปิดแอปครั้งแรกหลังเกิดเหตุแทน — เพิ่ม state ใหม่ `assignment_status = reassigned_away` (terminal สำหรับพนักงานคนเดิม ไม่นับเข้า success_rate) เก็บรายละเอียดไว้ดูย้อนหลังที่การ์ดในแท็บ "จบงาน" (เพิ่ม pill filter "ถูกโอนไป")
8. ~~**Push Notification จริง**~~ — **ปิดแล้ว** (สัมภาษณ์และออกแบบเสร็จสมบูรณ์ — ดู §15) สรุปสั้น: ใช้ **Web Push API** (ไม่ใช่ FCM) — Android/Desktop ใช้ได้เต็มรูปแบบ, iOS Safari ต้องเพิ่มลงหน้าจอโฮมก่อนถึงจะได้ push (ไม่บังคับ แค่แนะนำตอน onboarding) — **Fallback หลักคือ in-app notification** (badge/list ในแอป) ที่ใช้เสมอไม่ว่าจะได้ push หรือไม่ ไม่เพิ่ม channel สำรองอื่น (SMS/LINE Notify) ในเฟสนี้
9. ~~**QC Outcome**~~ — **ปิดแล้ว** (สัมภาษณ์และออกแบบเสร็จสมบูรณ์ — ดู §6.6, §7.6, §8, §10.1) สรุปสั้น: ไม่มีขั้น QC แยกก่อนปิดงานเป็นทางการ เพราะขั้นอนุมัติจ่ายเงิน (ไฟล์ 16/17) ทำหน้าที่ตรวจสอบในตัวอยู่แล้ว แต่เพิ่ม flow ตีกลับ 2 เส้นทางแยกตามประเภทปัญหา: `reject_expense` (เอกสารบัญชี/ใบเสร็จผิด — กระทบแค่ `expense.status`) และ `reject_evidence` (หลักฐานปิดงานน่าสงสัย — กระทบ `assignment_status` เป็น state ใหม่ `needs_revision`, field agent แก้ได้เฉพาะรูป/วิดีโอ/เสียง/รูปสินค้า ห้ามแก้เช็คอิน/outcome) — กรณี outcome ผิดจริงออกนอก scope ตั้งใจ ผู้จัดการจัดการนอกระบบ
10. **ไฟล์ 42 และ 43 (baseline เดิม) ถูก merge เข้าไฟล์นี้แล้วทั้งหมด** — ไฟล์ 42 (check-in/evidence/offline) merge สมบูรณ์ทั้งหมด ไฟล์ 43 (ปิดเคส/trigger finance/QC Outcome) merge สมบูรณ์ครบทุกส่วนแล้ว รวมเรื่อง QC Outcome ที่เพิ่งปิดในข้อ 9 ข้างต้น — ดู stub ของทั้งสองไฟล์สำหรับรายละเอียดเหตุผลการ merge
