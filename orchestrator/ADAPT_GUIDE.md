# คู่มือแปลงเอกสารโปรเจกต์ให้ใช้กับ RTB Orchestrator Dashboard

> **วิธีใช้เอกสารนี้:** เปิดไฟล์นี้ให้ AI (Claude Code หรืออื่น ๆ) อ่าน พร้อมชี้ให้มันดูสเปค/เอกสาร UI เดิมของคุณทั้งหมด แล้วสั่งว่า _"แปลงเอกสารทั้งหมดของฉันให้ตรงตามข้อกำหนดในไฟล์นี้ เพื่อให้ orchestrator dashboard ใช้งานได้เลย"_ — เอกสารนี้ระบุ **ฟอร์แมตที่ parser ต้องการเป๊ะ ๆ** + กฎการแบ่งงานไม่ให้กิน context + checklist ตรวจรับ

---

## 0. orchestrator ทำงานยังไง (บริบทที่ AI ต้องเข้าใจก่อนแปลง)

Orchestrator เป็นตัวสั่ง Claude Code ให้ทำงาน **ทีละ 1 task ต่อ 1 session** อัตโนมัติ:

```
อ่าน PROGRESS.md → หา "🎯 งานถัดไป" → สั่ง Claude Code ทำ (โดยอ่านเฉพาะเอกสารที่เกี่ยว)
   → รัน verify (typecheck/test/lint) → commit → merge → ทำ task ถัดไป
```

ดังนั้นเอกสารของคุณต้องถูกจัดให้:
1. **PROGRESS.md** — เครื่องอ่านได้ (parser ดึง "งานถัดไป" + ตารางสถานะ) — **สำคัญสุด ต้องตรงฟอร์แมต 100%**
2. **CLAUDE.md** — กติกา + ตารางเส้นทาง (task ไหนอ่านเอกสารไหน) + กฎกัน context ล้น
3. **WORKFLOW.md** — วงจรการทำงานต่อ session
4. **docs/** — สเปคละเอียด + INDEX + MAP (ให้อ่านเฉพาะช่วงบรรทัด ไม่อ่านทั้งไฟล์)
5. **reference/** — mockup/UI/โค้ดตัวอย่าง (มี MAP เช่นกัน)

**หลักการที่ต้องยึดตลอดการแปลง:** แต่ละ session มี context จำกัด (~200k tokens) ถ้าอ่านผิด/งานใหญ่เกิน จะเต็มก่อนลงมือ → งานพัง เอกสารต้องถูกออกแบบให้ "อ่านน้อย ทำพอดี"

---

## 1. PROGRESS.md — ข้อกำหนดฟอร์แมต (parser จับตามนี้เป๊ะ ห้ามเพี้ยน)

Parser ของ dashboard จับ pattern เหล่านี้ **ตรงตัวอักษร** — ถ้าไม่ตรง จะ parse ไม่ได้หรือได้ข้อมูลผิด

### 1.1 บรรทัด "อัปเดตล่าสุด" (ไม่บังคับ แต่ควรมี)
```
**อัปเดตล่าสุด:** 2026-07-25 — <สรุปสั้น>
```
- ต้องมี `**อัปเดตล่าสุด:**` ตามด้วยวันที่รูปแบบ `YYYY-MM-DD`

### 1.2 ตัวชี้ "งานถัดไป" — **บังคับ มีได้ตัวเดียว**
```
## 🎯 งานถัดไป — Phase <id>: <ชื่องาน>
```
- ต้องขึ้นต้น `## 🎯 งานถัดไป — Phase ` (อักขระ 🎯 และคำว่า "งานถัดไป" ต้องมี)
- `<id>` = ตัวเลขจุดตัวเลข + ตัวอักษรพิมพ์เล็กได้ 1 ตัว เช่น `1`, `1.2`, `2.5a`, `3.0`
- ตามด้วย `:` แล้วชื่องาน
- ใต้หัวข้อนี้ ใส่รายละเอียดพอให้เริ่มงานได้ (requirement + เอกสารอ้างอิง + ข้อควรระวัง)
- ✅ ถูก: `## 🎯 งานถัดไป — Phase 3.1: สร้าง Order (reservation/sale)`
- ❌ ผิด: `## งานต่อไป: Order` / `## 🎯 Next Task - Phase 3.1` (ต้องเป็นคำไทย "งานถัดไป")

### 1.3 หัว Phase — **บังคับ**
```
## Phase <key> — <ชื่อ Phase> [🔒]
```
- ขึ้นต้น `## Phase ` ตามด้วย key (ตัวเลขหรือตัวอักษรพิมพ์ใหญ่ เช่น `1`, `2`, `P`, `7`) แล้ว ` — ` (em dash หรือ hyphen) แล้วชื่อ
- ใส่ 🔒 ถ้า Phase นี้ล็อก (ห้ามเริ่มก่อน Phase อื่นเสร็จ)
- ✅ `## Phase 1 — Foundation 🔒 (ต้องเสร็จก่อน Phase 3)`

### 1.4 ตารางงานใต้แต่ละ Phase — **บังคับ 4 คอลัมน์**
```
| # | งาน | สถานะ | หมายเหตุ |
|---|---|---|---|
| 1.1 | ชื่องานสั้น ๆ | ✅ | วันที่ + commit `abc1234` + สรุป 1 บรรทัด |
| 1.2 | ... | 🔄 | ... |
| 1.3 | ... | ⬜ | ... |
```
- หัวตารางต้องเป็น `| # | งาน | สถานะ | หมายเหตุ |` (คำไทยตรงตัว)
- คอลัมน์ 1 = **id** รูปแบบเดียวกับ 1.2 (`1.1`, `2.5a`) — ถ้า id ไม่ตรงรูปแบบนี้ แถวนั้นจะถูกข้าม
- คอลัมน์ 3 = **สถานะ** ต้องมี emoji 1 ใน 4 ตัวนี้:
  - `⬜` = ยังไม่ทำ (todo)
  - `🔄` = กำลังทำ (doing)
  - `✅` = เสร็จ (done)
  - `⏸️` = ติดขัด/รอ (blocked)
- คอลัมน์ 4 = หมายเหตุ; commit hash ใส่ใน backtick `` `abc1234` `` (7–40 ตัว hex) parser จะดึงไปแสดง

### 1.5 ส่วน "บันทึกการตัดสินใจ" — ตัวหยุด parser
```
## บันทึกการตัดสินใจระหว่างพัฒนา
```
- ทุกอย่างหลังหัวข้อที่ขึ้นต้น `## บันทึกการตัดสินใจ` จะ**ไม่ถูกอ่านเป็น task** — ใช้เก็บ decision log ท้ายไฟล์

### 1.6 กฎ context ของ PROGRESS.md (สำคัญ)
- **ต้องบาง** — ไฟล์นี้ถูกอ่านทุก session = ต้นทุนคงที่ที่จ่ายตลอด แนะนำ **≤ 50,000 ตัวอักษร** (วัดด้วย `python3 -c "print(len(open('PROGRESS.md',encoding='utf-8').read()))"` ไม่ใช่ `wc -c` เพราะไทยหลายไบต์)
- รายละเอียดเต็มของงานที่ **เสร็จแล้ว** → ย้ายไป `docs/PROGRESS_ARCHIVE.md` เหลือใน PROGRESS แค่แถวตาราง (commit + สรุป 1 บรรทัด)
- ส่วน "🎯 งานถัดไป" ให้เหลือ **งานเดียว** เสมอ

## 2. CLAUDE.md — กติกา + ตารางเส้นทาง + กฎ context

Claude Code โหลดไฟล์นี้อัตโนมัติทุก session → ต้องกระชับ ต้องมี:

1. **กติกาห้ามละเมิด (non-negotiables)** ของโปรเจกต์ — สรุปกฎธุรกิจ/สถาปัตยกรรมที่ห้ามผิด เป็นข้อ ๆ สั้น ๆ
2. **ตารางเส้นทาง (งาน → อ่านเอกสารไหน)** — ตารางว่างานประเภทไหนต้องเปิด doc ไฟล์ไหน เช่น:
   ```
   | งาน | อ่าน |
   |---|---|
   | หน้า UI / component | docs/08 |
   | ฐานข้อมูล/schema | docs/03 |
   | หาช่วงบรรทัดก่อนอ่านไฟล์ใหญ่ | docs/00_MAP.md |
   ```
3. **กฎ context discipline (บังคับ — คัดลอกไปได้เลย):**
   - ห้ามอ่านไฟล์ใหญ่ทั้งไฟล์ — เปิด `docs/00_MAP.md` หาช่วงบรรทัดแล้ว `Read(offset, limit)` เฉพาะหัวข้อ
   - ค้นด้วย `Grep` ก่อนอ่านเสมอ ห้ามเปิดทั้งไฟล์เพื่อ "ดูว่ามีอะไร"
   - งานสำรวจ/วางแผนหลายไฟล์ = ใช้ **subagent** ให้มันอ่านในหน้าต่างของมัน แล้วส่งกลับแค่ข้อสรุป
   - ไฟล์ generated (migration/lockfile/snapshot/build) **ห้ามผ่าน context** — อ่านผ่าน `grep`/`head` เท่านั้น
   - แก้ไฟล์ใหญ่ = `Grep` หาจุดแล้ว `Edit` เฉพาะจุด ห้าม Read ทั้งไฟล์แล้ว Write ทับ
4. **กฎขนาดงานต่อ session** (ดูข้อ 4)

---

## 3. WORKFLOW.md — วงจรต่อ 1 session

ระบุลำดับที่ agent ต้องทำต่อ 1 ก้อนงาน:
1. อ่าน `PROGRESS.md` ส่วน "🎯 งานถัดไป"
2. หาเอกสารอ้างอิงจากตารางเส้นทางใน CLAUDE.md → ใช้ `docs/00_MAP.md` หา offset ก่อนอ่านไฟล์ใหญ่
3. วางแผนทีละขั้น (ระบุ section เอกสาร + วิธี verify) — งานใหญ่เกิน = แตกก่อน
4. ลงมือทำ + verify ทีละขั้น
5. รัน typecheck/test/lint ให้ผ่านทั้งหมด
6. อัปเดต PROGRESS.md (เปลี่ยนสถานะ + ย้ายรายละเอียดไป archive + cap "งานถัดไป" เหลืองานเดียว)
7. commit (conventional commits) + ระบุงานถัดไป

## 4. กฎการแบ่งงานให้พอดี context (หัวใจ — AI ต้องแบ่ง task ตามนี้)

เวลาแปลงสเปคเป็น "รายการ task ใน PROGRESS.md" **แต่ละ task ต้องจบได้ใน 1 session** เกณฑ์:

- **เพดานต่อ task: ~2,000 บรรทัดโค้ดใหม่** (ไม่นับ generated); เกิน ~2,500 = **ต้องแตกก่อน**เขียน
- **แต่ละ task ต้อง verify จบในตัว** — typecheck + test + commit ผ่านได้ด้วยตัวเอง
- **แนวการแตก** (พิสูจน์แล้ว):
  - **backend ก่อน → UI ตามทีหลัง** (ไม่ใช่แตกตามฟีเจอร์)
  - สูตร/ตรรกะสำคัญ = แยกเป็น pure module + test ก่อนเขียน router/UI
  - หน้าที่มีหลายแท็บ = แตกที่ขอบแท็บ
  - migration/schema = ก้อนแรกเสมอ
- **1 task = 1 headline ชัดเจน** เขียนในตารางได้ใน 1 บรรทัด
- ถ้าสเปคเดิมของคุณเป็นก้อนใหญ่ (เช่น "ทำหน้า Order ทั้งหน้า") AI ต้อง**ซอยเป็นหลาย task** เช่น 3.1a (backend), 3.1b (list/filter UI), 3.1c (modal) ฯลฯ

## 5. docs/ — สเปคละเอียด + INDEX + MAP

สเปค UI/ระบบเดิมของคุณ = ย้ายมาเป็นไฟล์ใน `docs/` (แบ่งตามหัวข้อ เช่น 01_ภาพรวม, 03_ฐานข้อมูล, 08_component, 09_หน้า/route ฯลฯ) แล้วต้องมี 2 ไฟล์คุม:

### docs/00_INDEX.md
- ดัชนีว่าไฟล์ไหนพูดเรื่องอะไร (1 บรรทัดต่อไฟล์) + ลำดับความสำคัญเมื่อเอกสารขัดกัน

### docs/00_MAP.md — **สำคัญสำหรับกัน context**
- ตารางช่วงบรรทัด (offset/limit) ของ **ไฟล์ใหญ่** ต่อหัวข้อ เพื่อให้ agent `Read(offset, limit)` เฉพาะที่ใช้ ตัวอย่าง:
  ```
  | ไฟล์ | หัวข้อ | บรรทัด |
  |---|---|---|
  | docs/03_DATABASE.md | §6 ตาราง orders | 420–512 |
  | reference/ui-mockup.html | ฟังก์ชัน renderOrderModal | 1840 |
  ```
- ไฟล์ไหนเกิน ~1,500 บรรทัด หรือ ~15KB = ควรมีใน MAP
- ระบุท้าย MAP ว่า "ถ้าแก้ไฟล์จนบรรทัดเลื่อน ต้อง regenerate MAP"

## 6. โปรโตคอลที่ agent ใช้คุยกับ orchestrator (ให้ AI รู้ไว้ ไม่ต้องใส่ในสเปค แต่ห้ามขัด)

Orchestrator ฝัง prompt ที่สั่งให้ agent ใช้เครื่องหมายพวกนี้ — เอกสารของคุณต้องไม่ไปสั่งอะไรที่ขัดกัน:
- `[[NEEDS_DECISION]] <คำถาม>` — agent พิมพ์เมื่อเจอจุดต้องให้คนตัดสินใจ (เอกสารไม่ชัด/ต้อง credential)
- `[[OPTIONS]] ก | ข | ค` — ตัวเลือกให้กด (เรียงตัวแนะนำก่อน ต่อท้าย "(แนะนำ)")
- `[[TASK_DONE]] <commit> <headline>` — เมื่อเสร็จ verify ผ่าน + commit แล้ว

ดังนั้นสเปคต้องออกแบบให้ **แต่ละ task จบด้วยการ commit ได้จริง** (มี test/วิธีพิสูจน์ชัดเจน) ไม่งั้น orchestrator จะถือว่างานยังไม่เสร็จ

## 7. คำสั่งสำหรับ AI ที่จะแปลงเอกสาร (ทำตามลำดับนี้)

1. **อ่านสเปค/เอกสาร UI เดิมทั้งหมดของฉัน** ทำความเข้าใจขอบเขตระบบ + ลำดับการพัฒนา
2. **จัดเอกสารเข้า `docs/`** แบ่งตามหัวข้อ + สร้าง `docs/00_INDEX.md` และ `docs/00_MAP.md` (ช่วงบรรทัดของไฟล์ใหญ่)
3. **ย้าย mockup/UI/โค้ดตัวอย่างเข้า `reference/`** + ใส่ใน MAP
4. **เขียน `CLAUDE.md`** — กติกาโปรเจกต์ + ตารางเส้นทาง + กฎ context discipline (ข้อ 2) + กฎขนาดงาน (ข้อ 4)
5. **เขียน `WORKFLOW.md`** ตามข้อ 3
6. **สร้าง `PROGRESS.md`** ตามฟอร์แมตข้อ 1 เป๊ะ:
   - แตกงานทั้งโปรเจกต์เป็น Phase → task ตามกฎขนาดข้อ 4 (แต่ละ task ≤ ~2,000 บรรทัด, verify จบในตัว, backend→UI)
   - ทุก task สถานะ `⬜` (ยังไม่ทำ)
   - ตั้ง "🎯 งานถัดไป" เป็น task แรกสุดที่ทำได้ (ไม่ติด lock)
   - ใส่ header + ตารางต่อ Phase + ส่วน "บันทึกการตัดสินใจ" ท้ายไฟล์
7. **ตรวจตัวเองตาม checklist ข้อ 8** ก่อนส่งมอบ

## 8. Checklist ตรวจรับ (ต้องผ่านทุกข้อ)

**PROGRESS.md**
- [ ] มี `## 🎯 งานถัดไป — Phase <id>: <title>` **ตัวเดียว** และ id ตรงรูปแบบ (`3.1`, `2.5a`)
- [ ] มีหัว `## Phase <key> — <name>` ทุก Phase
- [ ] ทุกตารางหัวเป็น `| # | งาน | สถานะ | หมายเหตุ |`
- [ ] ทุก id ในคอลัมน์แรกตรงรูปแบบ (เลข.เลข + ตัวอักษรพิมพ์เล็กได้)
- [ ] ทุกสถานะใช้ ⬜ / 🔄 / ✅ / ⏸️ เท่านั้น
- [ ] มี `## บันทึกการตัดสินใจ...` ท้ายไฟล์ (ถ้ามี decision log)
- [ ] ขนาดไฟล์ ≤ 50,000 ตัวอักษร (วัดด้วย python len ไม่ใช่ wc -c)

**การแบ่งงาน**
- [ ] ทุก task ประเมินแล้วว่า ≤ ~2,000 บรรทัดใหม่ + verify จบในตัว
- [ ] งานใหญ่ถูกซอย (backend→UI, pure logic แยก+test ก่อน router)
- [ ] Phase ที่ต้องทำก่อน ใส่ 🔒 + ระบุเงื่อนไข

**เอกสาร**
- [ ] มี `CLAUDE.md` (กติกา + ตารางเส้นทาง + กฎ context)
- [ ] มี `WORKFLOW.md`
- [ ] มี `docs/00_INDEX.md` + `docs/00_MAP.md`
- [ ] ไฟล์ใหญ่ทุกไฟล์มีช่วงบรรทัดใน MAP

**ทดสอบจริง:** หลังแปลงเสร็จ วางไฟล์ในโปรเจกต์ แล้วรัน
```
node orchestrator/orchestrate.mjs status
```
ต้องแสดง % ความคืบหน้า + "งานถัดไป" ถูกต้อง = แปลว่า parser อ่านได้ = พร้อมใช้กับ dashboard

## 9. หมายเหตุความเข้ากันได้
- Parser ปัจจุบันจับ **คำไทย** เป็น marker (`งานถัดไป`, `Phase`, `บันทึกการตัดสินใจ`, หัวตาราง `งาน/สถานะ/หมายเหตุ`) — เอกสารที่แปลงต้องใช้ marker เหล่านี้ตรงตัว (เนื้อหาข้างในเป็นภาษาอะไรก็ได้)
- คำสั่ง verify default = `pnpm typecheck / test / lint` ถ้าโปรเจกต์ใหม่ใช้ npm/yarn หรือคำสั่งอื่น ให้แก้ที่ `orchestrator/config.mjs` → `verify: [...]`
- `baseBranch` (default `master`) และรายชื่อโมเดล แก้ที่ `config.mjs` เช่นกัน
